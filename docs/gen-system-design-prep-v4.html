The v3 material at roughly half the length: reasoning framework, the application funnel, client state and storage, PII, attribution, and security. Same sections, trimmed to the facts.

Sections

Reasoning Framework

The five steps

Your job in an AI-augmented role is to impose enough structure that whoever writes the code can't get it subtly wrong. Run these in order on any vague prompt.

  1. Clarify and slice. Cut the problem into independent pieces; ask which one they want.
  2. Name the trust boundary. Who's untrusted, what they reach, where the guard sits.
  3. Draw the state grid. States by events, every cell filled.
  4. Locate the policy. The one rule with one owner vs mechanics you can duplicate.
  5. State the proof. How you'd verify each claim, and what your verification can't reach.

Step 1: Decompose into independent slices

Slices are independent when each has a distinct mechanism, is reviewable alone, is order-independent, touches non-overlapping files, and fails in isolation. Open with "there are several surfaces here, each ships and breaks on its own; which do you want?" That decomposes and hands the ambiguity back.

The six slices of the loan funnel
Input form (wizard). react-hook-form state, zod validation, masking, per-step POST, session persistence, a11y. Owns its step state machine; works with just a submit endpoint.
Offer fetch and render. Data fetching (React Query/SWR), discriminated-union state, derived sort/filter, stable keys, resilience. A read surface over an API; runs against a mock endpoint alone.
Attribution capture. URLSearchParams whitelist, httpOnly-cookie persistence, link decoration, Referrer-Policy, server lead-id. A cross-cutting carry-through tested by checking params survive navigation.
Apply / approval handoff. decorateUrl, the trust boundary (identifiers ride the URL, PII doesn't), redirect and return handling. The exit: consumes an offer id plus attribution, produces a redirect.
Telemetry. Event envelope (event_id, occurred_at), batching, sendBeacon, retry, sampling. Observes the others; none depend on it.
Session management. httpOnly session cookie, idle and absolute timeout, 401 detection, keep-alive warning. Wraps the flow; others just assume a session id exists.

Step 2: Name the trust boundary

Whenever PII or auth appears, recite three fields:

  • Untrusted principal: who crosses. For a web form, the browser, meaning the user and anything in their page.
  • Reachable surface: the endpoint they can hit. The submit API.
  • Enforcement point: the narrowest guard. Server-side validation and authorization at that endpoint, not the client schema.

The client zod schema is UX; the server schema is the authority. SSN never rides a URL, because the query string lands in logs and Referer headers.

Authentication is not authorization. "Valid logged-in user" differs from "allowed to touch this object"; the cross-user row is the classic gap (IDOR). The enforcement point must be narrow and low: a hidden button is cosmetic, because the principal reaches the server directly with curl.

Step 4: Locate the policy

One logical rule gets one owner; the mechanics of applying it can be copied freely.

  • Policy is the decision. "What counts as a showable offer" (present, not expired, eligible) is one isEligible(offer) predicate.
  • Mechanics is the application. Several card variants are fine.
  • Extract when the same rule hits 3+ places, or when layer-specific policy (a lender quirk) leaks into shared code. "Patching the same check in four places postpones three bugs."
Duplicated rule vs one owner 
// Drift: the same rule copied into three places
const visible  = offers.filter(o => o.fields && o.expiresAt > now && o.tier <= userTier)
const sortable = offers.every(o  => o.fields && o.expiresAt > now && o.tier <= userTier)
<ApplyButton disabled={!(offer.fields && offer.expiresAt > now && offer.tier <= userTier)} />
// change the rule and you must find all three, or they drift apart

// One owner: the policy lives once, mechanics just call it
const isEligible = (o) => Boolean(o.fields) && o.expiresAt > now && o.tier <= userTier
offers.filter(isEligible)
<ApplyButton disabled={!isEligible(offer)} />

Step 5: State the proof, and shape the tests

  • Behavioral proof over inspection: seed an expired offer and assert it's filtered. Reading the function isn't proof.
  • Red before green: a fix's regression test fails on old code, passes on new. Passing both ways proves nothing.
  • New branch, new test. Every error path or fallback gets one.
Red/green test and the test pyramid 
// Behavioral, red before green: fails on the bug, passes on the fix
test('expired offers are filtered out', () => {
  const offers = [{ id: 1, expiresAt: yesterday }, { id: 2, expiresAt: tomorrow }]
  expect(visibleOffers(offers, now).map(o => o.id)).toEqual([2])
})

Provenance over resemblance

Any check that grants permission, hides, classifies, or routes keys on a field written on purpose, not on something that looks right.

  • Provenance: a value stamped at the point of intent (server-set placement: 'sponsored', a canonical kind).
  • Resemblance: guessing from shape (id prefix, a color, an empty array). Breaks the day something else matches.
  • Authorize on the server's session claim, not a client-set flag. If you must infer, add a spoof test: a look-alike that must not trigger.

Verification ceiling, recourse, working with AI

  • Know your ceiling: your tests prove your code calls the lender API right, not that the lender honors the contract. A mock never proves a third-party contract; jsdom never proves browser-chrome behavior. When proof can't reach the owner, drop the claim, test the real surface, or flag the caveat.
  • Detection needs a recourse: an error banner needs a retry, an empty state a next action. An exit-less state is a dead end.
  • Working with AI: "I don't merge what the model wrote because it looks right; I review it adversarially and lean on deterministic checks it can't argue past: types, tests, lint, CI." Independent review beats self-review.
  • Meta-principle: make the bug unrepresentable. Discriminated unions, required props, types at the boundary, over tests that catch it later.
Jargon caveat: say the steps in plain language ("prove, don't assert," "every error needs an exit"), not framework names, which read as borrowed.

Multi-Step Application Flow

The wizard and the safe resume pattern

A form collecting an application over steps (income, employment, SSN) where answers survive step changes, refresh, and return. It's online: the server validates each step and the SSN goes straight to the server. The client holds a key; the server holds the data.

  • State persists across steps; progress saves after each so a refresh doesn't wipe it; resume continues where the user left off.
  • PII POSTs to the server after each step, persisted tokenized and keyed by session.
  • The client stores only a session id in an httpOnly, Secure, SameSite cookie, so XSS can't steal it.
  • Non-PII progress (step, loan amount) can sit in localStorage/sessionStorage.
  • Resume sends the session id; the server returns state. The SSN never re-enters the browser in plaintext; the user sees •••-••-1234.
  • Each step's status is explicit (untouched, valid, submitting, error) so no broken combination renders.

The rule: localStorage, sessionStorage, and IndexedDB are readable by any JS on your origin, so one XSS exposes them. Non-sensitive data can live there. PII never does. httpOnly cookies are invisible to JS, so session ids and the durable attribution copy live there. Anything sensitive stays server-side, with the client holding only the id that unlocks it.

PII Handling On The Client

GET vs POST, and iframe isolation

GET and POST are equally private on the wire (both TLS). GET puts values in the URL, which is written to history, access logs, and the Referer sent onward; POST keeps them in the body, which none of those record. So loggable identifiers (subid, clickid) go in a GET; applicant data (SSN, income) goes in a POST body.

  • iframe isolation: a cross-origin iframe has its own origin and DOM, so the host page's scripts can't read fields inside it. Pass attribution in via src, keep the SSN in the frame, post only non-sensitive events back via postMessage (set targetOrigin, validate event.origin).
  • A script SDK rendering into the host DOM gives styling control but lets host scripts read input, so it suits an offer carousel, not SSN capture.
  • Post-capture the value is tokenized server-side, so a token flows through the app instead of the SSN.

Attribution Capture

Capture, persist, re-inject

The lead source enters as URL params and must survive every hop to the lender handoff.

  • Capture: read known params once with URLSearchParams, against a whitelist.
  • Persist: an httpOnly cookie as durable copy, localStorage fallback, stamped first-seen so a later visit keeps first-touch.
  • Re-inject: decorate internal links and the outbound redirect so a stripped param still reaches the next page.
  • Don't rely on the referrer: the default Referrer-Policy (strict-origin-when-cross-origin) drops path and query cross-site, and lender hops are cross-origin.
  • The server mints a lead id and stores attribution against it, so the URL is a convenience and the server holds the record.
Models: first-touch credits the introducer; last-touch the final click (common in lead-gen billing); multi-touch splits it. Stitching an anonymous click to a later login happens server-side via an identity graph; the client carries both ids.

Event Collection

What the client owes for telemetry

An online funnel assumes connectivity. Telemetry still fires on flaky mobile, so it needs modest resilience, not an offline subsystem.

  • Each event carries a client event_id (UUID) for server dedup.
  • Batch and flush on a size or time threshold; retry with exponential backoff and jitter.
  • Flush on unload with navigator.sendBeacon(), which survives teardown that a normal fetch doesn't.
  • Stamp occurred_at so a late event still buckets correctly; sample low-value signals and record the rate.
Scope note: IndexedDB queues and Background Sync are for offline-first apps. A credit funnel assumes online; the resilience that matters is session and timeout handling.

Frontend Observability

What you watch in production, and how you find out fast

Telemetry (the Events section) is the plumbing that emits data; observability is knowing the app is healthy and catching a regression before users report it. Three pillars, plus the two frontend-forward surfaces.

PillarWhat it isFrontend surface
LogsTimestamped events and breadcrumbsConsole plus shipped to Sentry/Datadog
MetricsAggregated numbers over timeWeb Vitals, error rate, funnel counts
TracesOne request's path across servicestraceparent header propagated on fetch
  • Core Web Vitals, measured in the field with the web-vitals lib and reported as events: LCP < 2.5s (load), INP < 200ms (responsiveness, replaced FID in 2024), CLS < 0.1 (layout stability).
  • Error tracking: capture unhandled errors and promise rejections with breadcrumbs and a release tag; upload source maps so minified stack traces de-obfuscate. Sentry is the default.
  • Distributed tracing: the frontend mints and propagates a trace id via the W3C traceparent header on API calls, so a slow apply links to its backend spans.
  • Funnel metrics: step-complete, drop-off, offer-render, apply-click, riding the same event pipeline from the Events section.
  • Session replay (Sentry, LogRocket) reconstructs a bug from the user's real session.
  • SLOs and alerting: alert on error-rate spikes, Web Vitals regressions, and funnel drop; pair feature flags and canary releases to catch a bad deploy fast.
PII caveat: scrub PII before it leaves the browser. Replay and breadcrumbs capture SSN and income unless you mask them, so configure field masking and server-side scrubbing, and sample high-volume signals. In this domain a replay tool logging an SSN is a compliance incident.

Rendering The Offer List

Fetch, render, sort, filter, handle every state

The likely coding-round shape and their core surface.

  • Model the lifecycle as a discriminated union (idle, loading, success, error) so impossible states can't render. Render empty too: success with zero results shows "no offers match," not an error.
  • Sort with [...offers].sort() so React sees a new reference; offers.sort() mutates in place and the change is invisible.
  • Debounce the filter input (~300ms). Compute the sorted/filtered list during render from raw offers plus controls; storing it in effect-synced state is the classic stale-value bug.
  • Use the offer's canonical id as the key, never the array index. Virtualize only past hundreds of rows.
  • The apply link carries attribution via decorateUrl; applicant data never goes in it. Prefer skeletons over a spinner.

Validation And Input Masking

Two layers, one schema

  • Validate per-field on blur/change for feedback, per-step before advancing. Client validation is a convenience; the server's is the authority.
  • Declare rules once with zod, manage fields with react-hook-form (uncontrolled inputs via refs, so typing doesn't re-render the whole form).
  • Mask as-you-type (SSN ###-##-####, currency $1,234), keeping the raw value separate from the display.
  • Announce errors with aria-describedby and aria-invalid; move focus to the first error on submit. Validate an SSN without echoing it to a URL or log.

Server-side validation in Node/TS

Parse every inbound payload against a declared schema at the boundary, reject on failure, share one schema between the form and the route. zod is the default; valibot, Yup, Joi, ajv, and class-validator (NestJS) are alternatives.

// schema.ts — shared by the form (zodResolver) and the route
export const Application = z.object({
  income: z.number().positive(),
  ssn: z.string().regex(/^\d{3}-\d{2}-\d{4}$/),
})

// route handler — the real gate
const result = Application.safeParse(await req.json())
if (!result.success) return Response.json({ errors: result.error.flatten() }, { status: 400 })
const data = result.data // typed and validated past this line

Parameterized queries stop SQL injection

Validation checks shape; parameterization stops input being read as code. Separate defenses, both needed. Never concatenate user input into a query.

// Vulnerable: input becomes SQL; "' OR '1'='1" returns every row
db.query(`SELECT * FROM users WHERE email = '${email}'`)

// Safe: the driver binds the value as a parameter
db.query('SELECT * FROM users WHERE email = $1', [email])

// An ORM parameterizes for you
prisma.user.findUnique({ where: { email } })

Slow Or Failing Partner API

Online resilience

  • Time out with AbortController plus a timer; show a loading state with skeletons immediately.
  • On error, show a message and retry button; auto-retry transient failures with backoff. Distinguish types: 4xx don't retry, 5xx/timeout do, network error means offline.
  • Render partial results: if one partner fails, show the offers that returned.
  • Wrap subtrees in an error boundary so a render crash shows a fallback, not a blank screen.
  • Show cached offers while refetching (stale-while-revalidate via React Query/SWR). Cancel the previous request when the query changes.

AbortController vs a generation counter

Both stop an old response overwriting a newer one, at different points.

  • AbortController cancels the in-flight request when a new one starts; the promise rejects with AbortError, freeing the connection. The primary tool: it prevents wasted work.
  • Its limit: it only helps if you cancel in time. A response already mid-processing, or an A→B→A repeat you can't tell apart by value, can slip through.
  • A generation counter increments on each query change; a request captures the value and, on resolve, discards its result if the value moved. It decides whether to apply, catching the ABA case.
  • Complementary: abort cancels the work, the counter commits only the latest result. React Query/SWR do both for you.

Session Management And Timeouts

Identity across requests

  • A session is a server record keyed by an id in an httpOnly cookie the browser sends automatically.
  • Idle timeout expires after inactivity (financial apps ~15 min); absolute timeout expires a fixed time after login regardless of activity.
  • On expiry: detect the 401, show "session expired," keep non-PII progress, prompt re-auth, resume. Warn first with a keep-alive modal.
  • Server session (opaque id, easy to revoke) vs JWT (self-contained, hard to revoke, so short expiry plus refresh).

Cookie Flags

The attributes

  • httpOnly: JS can't read it via document.cookie. Use for session ids.
  • Secure: sent only over HTTPS.
  • SameSite: Strict never sends cross-site; Lax sends on top-level navigations only; None always sends and needs Secure. Lax/Strict mitigate CSRF.
  • Domain/Path: scope which URLs get it. Expires/Max-Age: lifetime; no expiry means it dies on browser close. ~4KB, so store an id, not data.
Why Lax is the default: Strict withholds the cookie when a user arrives from any other site (their email, a partner link), so they land logged out. Lax sends it when following a link but not on cross-site subrequests, stopping CSRF while keeping arrivals working. Browsers default to Lax when the attribute is omitted.

httpOnly lifecycle, and signed cookies

An httpOnly cookie lives in the HTTP layer; JS is bypassed but the cookie stays active.

  • Created: server sends Set-Cookie; the browser stores it out of JS reach. Sent: auto-attached as the Cookie header on every matching request. Deleted: another Set-Cookie with Max-Age=0.
  • Cross-origin fetch sends it only with credentials: 'include' plus the server's Access-Control-Allow-Credentials.

Signed cookies carry an HMAC the server computes with a secret; on return it recomputes and rejects a mismatch. This protects integrity, not confidentiality (the value stays readable). It stops a user editing user_id=42 to 43. Different job from httpOnly (which stops reading), often paired. For an opaque random session id it adds little, since the id is already unguessable and the data lives server-side; it earns its keep when the cookie itself carries data. A JWT is the same idea in a standard format.

XSS And CSRF

XSS: an attacker runs their script in your page

Injected script runs with your origin's privileges: it reads localStorage, non-httpOnly cookies, and keystrokes. On a PII form that's a direct SSN leak.

  • Escape output. React escapes by default; avoid dangerouslySetInnerHTML, sanitize with DOMPurify if you must render HTML.
  • Set a CSP to restrict script sources; keep session ids in httpOnly cookies.
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  style-src 'self' 'unsafe-inline';
  connect-src 'self' https://api.example.com;
  frame-ancestors 'none';
  object-src 'none'; base-uri 'self';
  upgrade-insecure-requests;
  • script-src 'self' 'nonce-...' is the core control: only your scripts and nonce-carrying inline scripts run, so injected <script> is refused (Next.js sets the nonce via middleware).
  • frame-ancestors 'none' blocks clickjacking; connect-src blocks exfiltration; object-src/base-uri close bypass routes.
  • Keep 'unsafe-inline' off script-src; it gives back most of the protection. It's tolerable on style-src.

CSRF: an attacker makes the browser send an unintended request

Because the browser auto-sends cookies, a malicious page can trigger an authenticated request on the user's behalf.

  • SameSite=Lax/Strict so the cookie isn't sent cross-site. The baseline.
  • Synchronizer token: a per-session secret the server embeds in the page and requires back on state-changing requests. A cross-site page can't read your DOM, so it can't forge it. The stateless double-submit variant puts the token in a cookie and echoes it in a header.
  • Origin/Referer check on POST/PUT/DELETE: compare to your origin, reject a mismatch. A cheap second layer.

In practice: SameSite baseline, a token for sensitive actions, Origin behind both. Note POST isn't "more secure" than GET; GET is just worse for one reason, data resting in the URL.

Accessibility

Keyboard and screen-reader support (ADA/WCAG)

  • Every input has a real <label> tied by htmlFor/id.
  • Announce errors: aria-describedby links the message, aria-invalid marks the field, role="alert" or an aria-live region speaks dynamic ones.
  • Keyboard-operable with a visible focus ring and logical tab order; masked inputs get a format hint, not raw punctuation.
  • Never signal an error by color alone. WCAG 2.1 AA is the bar; test keyboard-only, with a screen reader, and axe DevTools.

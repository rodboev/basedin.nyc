Architecture

Architectural decisions and patterns across projects.

Sections

scheduling-v2: Three-Tier API

The scheduling optimizer splits data loading, expansion, and optimization into three chained API endpoints. Each tier consumes the previous one's output and adds a distinct layer of processing, so any tier can be called independently for debugging or by different parts of the frontend.

Tier 1: /api/serviceSetups — Raw Data

Queries SQL Server (via FreeTDS/ODBC), joining ServiceSetups, Locations, Schedules, Technicians, and FrequencyClasses into flat rows. Each row is normalized: DB field names become consistent camelCase, TimeRange strings are parsed into [rangeStart, rangeEnd] second offsets, WorkTime is converted to Eastern time, and per-setup tech assignment overrides are merged from an enforcement state file. Results are disk-cached to data/serviceSetups.json so subsequent calls skip the database entirely.

Output: an array of normalized service setup objects, one per recurring service contract.

Tier 2: /api/services — Temporal Expansion + Spatial Grouping

Calls Tier 1 internally, then expands each setup into concrete dated service instances for a requested date range. For each setup it walks the range day by day, checking a 420-character schedule bitmap string to determine whether that service occurs on that date. Matching dates get a concrete start/end datetime calculated from the preferred time and duration, rounded to 15-minute increments.

Additional processing at this tier:

  • Filters services outside configured NYC boroughs
  • Removes techs with exact time collisions (duplicate scheduling artifacts)
  • Fetches the pairwise Haversine distance matrix from /api/distance-matrix for all unique locations
  • Runs a geographic + time-compatibility grouping pass, clustering services within a hard max radius while respecting time windows

Output: a flat array of dated service objects with resolved times, locations (parsed float coordinates), tech assignments, and embedded distance data.

Tier 3: /api/schedule — Optimization

Calls Tier 2, filters out invalid entries (bad time ranges, missing coordinates, out-of-range dates), then hands valid services plus a full distance matrix to a Node.js worker thread for the heavy scheduling work:

  • Separates long services (above a threshold) into solo shifts
  • Sorts remaining services by time-window flexibility, least flexible first
  • Places each service into existing shift gaps using travel time, distance, and scoring
  • Runs iterative shift-merging passes to consolidate toward ~12 services per tech
  • Assigns tech IDs across days with continuity scoring (start-time similarity, workload balance, geographic proximity to prior day)
  • Compresses each shift by condensing services toward the midpoint

Output: fully sequenced services with cluster assignments, tech IDs, sequence numbers, and travel metadata (distance and time from previous service).

Data flow

SQL Server (FreeTDS/ODBC)
  └── /api/serviceSetups   raw DB rows → normalized setup objects (disk-cached)
        └── /api/services  setups → dated service instances, geographic grouping
              │
              ├── /api/distance-matrix  pairwise Haversine distances (in-memory cached)
              │
              └── /api/schedule         filters + worker thread optimizer
                    └── worker.js       shift building, merging, tech assignment, condensing
                          └── frontend  drag-and-drop schedule UI

Why three tiers?

Each tier has a different change frequency and failure mode. The raw data layer caches aggressively and rarely changes shape. The expansion layer is date-range-dependent and handles the combinatorial explosion of "which services happen when." The optimization layer is CPU-intensive and runs in a worker thread to avoid blocking the event loop. Separating them means you can debug each layer independently: hit /api/serviceSetups to verify the data looks right, hit /api/services?start=...&end=... to see what got expanded, and only then check whether the optimizer assigned them sensibly.

notes-ai: Content-Addressed LLM Pipeline

Internal tool for Liberty Pest Control. Field techs submit service notes via PestPac; the app pulls those notes, runs them through an LLM to draft personalized upsell emails, lets staff edit in a rich text editor, and sends via Gmail. A voice feature calls customers to summarize the visit and pitch follow-up services.

Stack

Next.js 15 RC + React 19 RC with the experimental React Compiler, wrapped in a custom Node HTTP server. GPT-4o for email generation, OpenAI Realtime API for voice. SQL Server (PestPac) via SSH tunnel for source data, Supabase (PostgreSQL) for durable persistence. Hosted on Heroku. (Later retrofitted to DeepSeek + ElevenLabs to cut demo costs, but the architecture was built around the OpenAI APIs.)

Content-addressed caching

Every note is SHA-1 hashed with object-hash. That fingerprint becomes the universal key across every layer: in-memory Map, disk data/*.json, Supabase primary key, React Query cache key, URL query param, and an injected x-fingerprint request header. Reads cascade memory → disk → Supabase, writing back up the chain on miss. Heroku's ephemeral filesystem serves as a warm session cache; Supabase is the durable fallback across dyno restarts. Identical note content fetched on different days hits cache rather than re-generating.

SSE + partial JSON for progressive LLM output

Uses browser-native EventSource (one-way SSE) rather than WebSocket for streaming GPT-4o tokens to the client. Notes are chunked (10 at a time, 3 in dev), each chunk streamed through ReadableStream in the API route. best-effort-json-parser renders partial email JSON as tokens arrive before the response is complete, so emails surface progressively rather than all-at-once.

Voice: signed URL pattern

The call button hits GET /api/voice/signed-url, which mints an ephemeral OpenAI Realtime API WebSocket URL server-side. The client connects directly with that URL. The private API key never touches the browser. Per-note context is injected as prompt overrides at session start, and a module-scope singleton enforces one active call globally without Redux or Context.

LLM call design

response_format: { type: 'json_object' } forces structured output. Address fields are stripped before notes reach the LLM (privacy). seed: 0 for reproducibility. System prompts use {{email.current}} and {{error}} template slots expanded by a recursive expand() function, and prompts are user-editable via a Settings panel persisted to Supabase.

Demo mode via React Context

?demo=true activates DemoProvider; useNotes and useEmails swap to demo endpoints serving fabricated data and skip all Supabase writes. No if (demo) scattered through components.

Data flow

SQL Server (PestPac, via SSH tunnel)
  └── /api/notes              raw service notes, normalized
        └── /api/emails       LLM generation (GPT-4o, SSE-streamed)
              │
              ├── TinyMCE     rich text editing, staff review
              │
              ├── Gmail API   send approved emails
              │
              └── /api/voice/signed-url → OpenAI Realtime WebSocket
                    └── browser   direct voice connection

Cache reads: memory Map → disk JSON → Supabase (fingerprint-keyed at every layer)

pr-sweep: Autonomous Multi-Agent PR Pipeline

Fully autonomous, multi-agent pipeline for making upstream open-source contributions. Runs continuously from issue discovery through code, review, PR opening, and post-push convergence. 240 PRs across 3 repos, 196 shipped, 97% acceptance rate.

Subskill chain

The pipeline is a chain of six skills, each handing off to the next. Only pr:converge can declare completion for pushed work.

pr:find       scoped status reconciliation, then scout agents per search dimension
    │
pr:spec       planner agents write 4-file artifact bundles per target
    │
pr:code       coder agents implement in isolated git worktrees
    │
pr:review     cross-provider adversarial review, fixups, push, open PR
    │
pr:converge   shared post-push loop: CI, bots, merge, reviewer feedback

pr:rework     triggered by reviewer feedback on existing PRs
    │
pr:converge   same shared terminal phase

Model tiering and cross-provider review

Five agent tiers across three host runtimes (Claude Code, Codex CLI, MiMoCode). Scouts run on Sonnet for cheap search. Planners run on Opus for spec quality. Coders run on Haiku for speed. The adversarial reviewer is always the opposite model family from the orchestrator: if the orchestrator is Claude, the reviewer is GPT-5.5 dispatched via shell (not as a subagent) for a genuinely independent pass. Up to 5 coder and reviewer agents run concurrently per phase.

Five-gate discovery

Scout agents search in parallel across dimensions (labels, subsystems, bug clusters). Every candidate must pass five gates in order:

  1. Freshness: the specific file, function, and line range must still exhibit the bug on current origin/{default_branch}
  2. Issue thread: full thread read, not just the body. Kill signals: "fixed", "resolved", "duplicate", "claimed", "wontfix"
  3. Closed work: searches closed PRs and sibling issues by keyword, affected files, function names, error strings
  4. Competing PRs: searches open PRs addressing the same surface
  5. Claimed work: distinguishes active ownership from courtesy holds (bare offer older than 14 days with no follow-up)

Survivors are tiered: maintainer direction > architectural > feature > bugfix > janitorial.

Spec artifacts

After target approval, planner agents write four files per target: an implementation plan with file:line anchors pinned to current HEAD, a PR body in the repo's observed format (passed via --body-file, never inline), an execution prompt for the coder agent (worktree setup, file allowlist, test commands, repo-specific gates), and optionally an issue file when no upstream issue exists.

Code phase

Before dispatching coders, the orchestrator audits the target set as a group, classifying each as independent, stacked, serialized, or hold. Only independent targets dispatch. Each coder works in an isolated git worktree. Workers stage but never commit; the orchestrator owns all commits after review passes. Each session re-verifies freshness independently to guard against batch staleness.

Post-push convergence

After any push or PR update, the skill that pushed hands off to pr:converge rather than running its own convergence logic. The loop polls every 2 minutes for at least 6 minutes: CI check state, merge state, PR comments, reviews, and review threads (GraphQL thread-level resolution). A complete poll cycle finishes before acting on any signal; if both a failing check and actionable feedback appear in the same cycle, the feedback is handled first since the resulting push gives a cleaner CI rerun.

Bot comments are fingerprinted (author + body hash) to avoid re-triaging. Stop conditions: 2 fix-push cycles per PR, 3 consecutive quiet poll cycles, fabricated results (immediate stop), or human maintainer signals like "duplicate" or "spam" (stop entire repo, trigger survival audit).

Continuation guard

Pipeline continuation is enforced at the harness level via Stop hooks, not by prompt instructions alone. Every subskill declares a Stop hook that calls a shared guard script. The guard inspects execution state and exits 0 (allow stop) or 2 (block stop with a reason). Only four markers can end a run: convergence complete, status reconciliation, approval gates (target selection, survival audit), and discovery complete with no candidates. Everything else is blocked. This decouples continuation discipline from model capability, so lighter models can run the pipeline without self-assessing as done prematurely.

Per-repo config

Four config files per repo: config (identifiers, git paths, test runner, bot definitions with trigger timing and triage rules, convergence intervals, quirks), find (search dimensions with verified label strings and issue counts, skip rules), style (conventions observed from actual merged PRs, each claim URL-cited), and templates (exact structure for artifact files, cross-file requirements).

Data flow

GitHub Issues
  └── pr:find        scout agents per search dimension, 5-gate filtering
        └── pr:spec  planner agents → 4-file artifact bundle per target
              └── pr:code     coder agents in isolated worktrees (stage only, never commit)
                    └── pr:review   cross-provider adversarial review, commit, push, open PR
                          └── pr:converge   poll CI + bots + reviews, fix-push cycles
                                └── merged / pr:rework → pr:converge (on reviewer feedback)

Stop hooks: continuation-guard.js blocks premature exit at every phase

Prose Examples

pr-sweep

Most recently, I built a multi-agent orchestration system that autonomously contributes to open-source projects end-to-end. It discovers issues, researches codebases, writes implementation specs, builds code in isolated worktrees, runs cross-provider adversarial reviews, opens PRs, then holds control through a convergence loop that triages CI failures, bot reviews, merge conflicts, and reviewer feedback until the PR is clean or a human decision is needed. Stop hooks enforce deterministic continuation at the harness level so the system can't self-assess as done and stop early. Over 200 PRs shipped to production across 3 repos at 97%+ acceptance.

notes-ai

Before that, I built an internal AI tool that pulls field technician service notes from a legacy database, streams them through GPT-4o to draft personalized customer emails (SSE with partial JSON parsing so results render progressively), and makes follow-up voice calls through the OpenAI Realtime API using a signed-URL pattern that keeps API keys server-side while giving the browser a direct WebSocket connection. Every note is SHA-1 fingerprinted, and that hash serves as the universal key across the in-memory cache, disk cache, Firebase primary key, and React Query cache.

I'm interested in the idea of a system where AI agents, clinicians, and data work together to deliver care at scale. I've built internal platforms on a smaller scale, bridging legacy data back-ends with frontier models to write customer-facing communications and make phone calls. These are novel opportunities with broad applications; I've worked on solving some of these problems already, and am interested in applying my learnings on a larger scale.

Most challenging project (application, June 2026)

I build a scheduling engine for a company that deploys 100 technicians a day throughout the NYC metro area. It's a vehicle routing problem with additional constraints: time windows, geographic continuity, workload balance, tech-to-account relationships and service durations. The core algorithm is several thousand lines running in Node.js worker threads, doing gap-packing with weighted scoring, two-phase shift merging, and tech assignment with continuity scoring across days. There was no off-the-shelf solver or solution to do this, so I wrote it from scratch. The real challenge was solving for every optimization, since one dimension degrades another, and searching for the least-bad tradeoff across all of them simultaneously.

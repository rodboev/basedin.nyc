Search, Retrieval & Ranking

The role's core output: "scalable frameworks for retrieval, reranking, and LLM-driven evaluation to deliver highly personalized and high-quality results." This is search infrastructure with an AI layer on top.

Elasticsearch fundamentals

  • Inverted index: the core data structure. Documents are analyzed (tokenized, stemmed, normalized) at index time. Queries run against the index, not raw documents. Field mappings control how text is analyzed.
  • Query DSL: bool queries compose must/should/filter/must_not clauses. filter is cached and doesn't affect scoring; must/should contribute to relevance. function_score wraps a query to boost by arbitrary signals (recency, funding amount, investor reputation).
  • Aggregations: faceted search (group by industry, stage, location), metrics (avg funding, median headcount), nested aggregations for drill-down. Run alongside search results in a single request.
  • Relevance tuning: BM25 is the default scoring algorithm. Custom scoring via function_score, script_score, or learning-to-rank plugins. The gap between "returns results" and "returns the right results in the right order" is where the engineering lives.

Hybrid search (keyword + vector)

Pure keyword search misses semantic matches ("AI startup" won't find "machine learning company"). Pure vector search loses precision on exact terms (company names, investor names, specific technologies). Hybrid search combines both:

  • Embedding models: encode documents and queries into dense vectors. OpenAI embeddings, Cohere Embed, open-source models (BGE, E5, GTE). The JD mentions experimenting with embedding models, which means they're actively evaluating which model produces the best retrieval for their domain.
  • Elasticsearch dense_vector: native kNN search since ES 8.0. Store embeddings alongside text fields, run hybrid queries that combine BM25 text scoring with vector similarity.
  • Reciprocal Rank Fusion (RRF): merge ranked lists from different retrieval methods without needing comparable scores. Each result's fused score = ∑ 1/(k + ranki). Simple, effective, no tuning needed for the fusion step itself.

Reranking

First-stage retrieval (keyword, vector, or hybrid) is fast but coarse. Reranking takes the top-N candidates and applies a more expensive, more accurate model:

  • Cross-encoders: take (query, document) pairs and output a relevance score. More accurate than bi-encoders (embedding models) because they see both inputs together, but too slow to run over millions of documents. Cohere Rerank, Jina Reranker, open-source models.
  • LLM-as-reranker: prompt an LLM to rank a list of candidates by relevance to the query. More flexible (can incorporate complex criteria like "prefer companies with recent funding rounds in climate tech"), more expensive. This is likely what Harmonic means by "LLM-driven evaluation."
  • Personalization layer: reranking isn't just relevance to the query; it's relevance to the user. A VC focused on Series A climate tech should see different rankings than one focused on seed-stage fintech, even for the same query. User preference vectors, interaction history, portfolio overlap.

The architecture (multi-stage pipeline, model selection by task cost, deterministic quality gates) translates directly to search ranking infrastructure.

Agent-Based Systems

The JD: "agentic layer for startup search and research," "dynamic agentic frameworks purpose-built for venture," "AI-first product workflows." Scout is an agent system.

Agent architecture

  • The loop: prompt → LLM decides action → execute tool → observe result → repeat until done. The orchestrator manages this loop, enforces tool permissions, handles timeouts, and captures the trace.
  • Tool use: the agent has access to a set of tools (functions with schemas). The LLM receives tool definitions in its system prompt, calls them by emitting structured JSON, and the orchestrator executes the function and returns the result. MCP (Model Context Protocol) standardizes tool discovery and invocation across providers.
  • Multi-agent: multiple specialized agents collaborate. A planner agent decomposes a task, worker agents execute subtasks, a reviewer agent validates output. Communication patterns: shared scratchpad, message passing, or a coordinator that routes between agents.
  • Memory: the JD explicitly lists "memory systems" as a discovery area. Short-term (conversation context), medium-term (task state persisted across turns), long-term (vector store for retrieval). For Scout, memory means: what has this VC searched before, what companies have they already evaluated, what preferences have they expressed implicitly through interaction patterns.

LangChain / LangGraph

  • LangChain: the dominant Python framework for LLM applications. Chains compose prompts, models, and output parsers. Retrievers abstract over vector stores and search engines. The LCEL (LangChain Expression Language) pipes components together: retriever | prompt | model | parser.
  • LangGraph: adds stateful, graph-based agent workflows on top of LangChain. Nodes are functions, edges are conditional transitions. State is explicit and checkpointable. Supports cycles (agent loops), branching (conditional tool selection), and human-in-the-loop (pause, get approval, resume). This is the framework for Scout's agentic flows.
  • Parallel to pr-sweep: pr-sweep's orchestration (multi-phase pipelines, conditional branching, deterministic gates, state tracking across agent turns) is the same computational model as LangGraph. The difference is framework vs. custom implementation. LangGraph adds checkpointing, streaming, and a standard graph abstraction; pr-sweep built these from scratch.

Agent orchestration in a product context

Scout isn't an internal tool; it's a product VCs interact with. The engineering challenges beyond "make the agent work":

  • Streaming: agent reasoning visible to the user in real time. Progressive disclosure of sources, intermediate findings, confidence signals.
  • Cost control: token budgets per query, model routing (cheap models for simple lookups, expensive models for synthesis), caching of repeated retrievals.
  • Reliability: the JD's priority order is "reliability, performance, cost, and then developer productivity." Agent loops can hang, hallucinate, or loop indefinitely. Circuit breakers, iteration limits, fallback paths.
  • Deterministic replay: reproducing agent behavior for debugging and evaluation. Log the full trace (prompts, tool calls, responses, timing) so you can replay a session without hitting the LLM again.

Evaluation Pipelines

The JD: "Improve and extend our evaluation pipelines to test new models and determine lifts in specific parts of our product." This is the gap area. Frame it as systems engineering with an ML flavor, not ML research.

What eval means here

Harmonic isn't training foundation models. They're evaluating which models, prompts, embeddings, and retrieval strategies produce the best results for their specific domain (startup data for VCs). This is applied engineering: build the harness, define the metrics, run the experiments, measure the lift.

Retrieval evaluation metrics

  • MRR (Mean Reciprocal Rank): 1/rank of the first relevant result, averaged across queries. Measures "how quickly does the user find what they want?"
  • NDCG (Normalized Discounted Cumulative Gain): measures ranking quality with graded relevance (not just relevant/irrelevant). Penalizes relevant results appearing lower in the list. The standard metric for search quality.
  • Precision@k / Recall@k: of the top k results, how many are relevant (precision) and what fraction of all relevant results appear (recall).
  • MAP (Mean Average Precision): average precision across all recall levels. Captures both precision and recall in a single number.

LLM evaluation

  • LLM-as-judge: use a strong model to grade the output of the model being evaluated. Define rubrics (relevance, completeness, factual accuracy), score on a scale, aggregate across a test set. Cheaper and faster than human evaluation, correlates well for many tasks.
  • A/B testing prompts and models: same query, different configurations. Compare outputs on the eval metrics. Statistical significance matters: small test sets produce noisy results.
  • Regression testing: a new model or prompt shouldn't break cases that previously worked. Golden sets of query/expected-result pairs. Run after every change, flag regressions.
  • Domain-specific challenges: startup data is noisy, incomplete, and constantly changing. A company's description six months ago may not reflect what they do now. Ground truth is expensive to curate and goes stale.

How pr-sweep maps

pr-sweep's review gates are an eval pipeline for code quality: define criteria, run multiple evaluators (cross-provider adversarial review), aggregate scores, gate on thresholds, track regressions. The infrastructure pattern (harness, metrics, gates, iteration) is the same; the domain (code quality vs. search relevance) is different. The honest framing: "I've built evaluation infrastructure, not retrieval-specific benchmarks. The engineering is transferable; the domain metrics are new to me."

PostgreSQL and Data Modeling

Postgres is in the stack alongside Elasticsearch. Likely split: Elasticsearch for search and ranking, Postgres for structured data (user profiles, saved searches, interaction history, agent traces, workflow state).

Relevant Postgres features

  • JSONB: agent traces, tool call logs, and LLM responses are naturally JSON. JSONB columns with GIN indexes for querying inside documents. Tradeoff: flexibility vs. referential integrity.
  • Partitioning: tens of millions of companies, hundreds of millions of operators. Time-based or hash partitioning for query performance on large tables.
  • Materialized views: precomputed aggregations (company scores, investor activity summaries) refreshed on a schedule. Useful for dashboard-style queries that would be too expensive to run live.
  • Advisory locks: coordinate agent execution. Ensure only one agent processes a given research task without locking rows.
  • CTEs and window functions: multi-step analytical queries. Ranking companies within cohorts, computing percentiles, tracking metric changes over time.
  • pgvector: if they store embeddings in Postgres alongside Elasticsearch. Vector similarity search within the relational database for cases where the full ES index isn't needed.

dbt

dbt (data build tool) manages SQL transformations as version-controlled models. Each model is a SELECT statement that defines a table or view. dbt handles dependency ordering, incremental builds, testing (schema tests, data tests), and documentation. It sits between raw ingested data and the clean, structured tables that the application queries. For Harmonic, dbt likely transforms raw company/investor data from hundreds of sources into the canonical models that power search and Scout.

Domain: Business Dissolution

Shutting down a company is a multi-step, multi-party, jurisdiction-dependent workflow. The product automates and orchestrates what used to require manual coordination across legal, accounting, tax, and state agencies.

What the workflow involves

  • State filings: articles of dissolution, certificate of cancellation, or equivalent, varying by entity type (LLC, C-corp, S-corp) and state of incorporation. Delaware, California, New York each have different forms, fees, timelines, and prerequisites.
  • Tax clearance: state and federal tax obligations must be settled before dissolution is accepted. IRS requires a final return (Form 966 for corps). States may require tax clearance certificates.
  • Creditor notification: many states require formal notice to known creditors and sometimes published notice for unknown creditors. Statutes define minimum waiting periods (typically 60–120 days).
  • Asset distribution: remaining assets distributed to shareholders/members after debts are settled. Order of priority is legally prescribed.
  • Employee/contractor obligations: final paychecks, COBRA notifications, W-2 or 1099 preparation, benefits termination.
  • Registered agent cancellation, EIN closure, bank account closure, SaaS subscription cancellation, IP disposition.

What this means for the product

The platform is a stateful workflow engine. Each dissolution is a long-running process (weeks to months) with dependencies between steps, jurisdiction-specific rules, waiting periods, and external blocking conditions. Think of it as a project management tool where the project template varies by entity type and state, steps have legal deadlines, and some steps require integration with government systems or third-party services.

Compliance Workflows as Code

The JD asks for someone who can "translate requirements into scalable technical solutions." In this domain, the requirements are legal rules that vary by jurisdiction and change over time.

The core engineering problem

  • Rule engines: dissolution steps, prerequisites, deadlines, and required documents are governed by state statutes. Encoding these as data (rule tables, decision trees, state machines) rather than hardcoded conditionals makes the system maintainable as laws change and new states are added. A rule engine separates the "what" (legal requirements) from the "how" (execution logic).
  • Workflow orchestration: steps have dependencies (can't file dissolution until tax clearance is obtained), waiting periods (creditor notice period must elapse), and external triggers (state agency responds). This is a DAG (directed acyclic graph) execution engine, similar to CI/CD pipelines or data orchestration tools like Airflow, but with human-in-the-loop steps and much longer timescales.
  • Jurisdiction as configuration: the same logical step ("file articles of dissolution") has different concrete implementations per state. The system needs an abstraction layer where adding a new state means adding configuration, not rewriting application code.
  • Audit trail: every action, decision, and state transition needs to be recorded immutably. When a dissolution is challenged or audited, the system needs to reconstruct exactly what happened and when.

Where this gets interesting

SimpleClosure is essentially building legaltech infrastructure. The "simple" in the name is the UX goal; the underlying system is handling genuine complexity. This is the kind of product where getting the state machine wrong doesn't just cause a bug, it causes legal exposure for the client.

Third-Party Integrations

The JD calls out "connecting with third-party services" as a backend requirement. In this domain, integrations are load-bearing.

  • Carta: cap table management. When a company dissolves, equity needs to be resolved: cancel outstanding options, distribute remaining assets to shareholders per ownership percentages. Carta integration pulls the cap table and ownership data.
  • Payroll/HR providers: final payroll runs, benefits termination, COBRA administration. ADP, Gusto, Rippling APIs.
  • State agency portals: many states now accept electronic filings. Some have APIs; others require form-filling or even mailed documents. This is where document generation (the PDF repos) becomes critical.
  • Banking: Brex is in their stack. Account closure, final disbursements, wire transfers for asset distribution.
  • Accounting: QuickBooks, Xero integration for final financial statements and tax preparation data.

Integration engineering patterns

Each third-party integration is a boundary with different reliability characteristics, rate limits, authentication schemes, and data formats. Standard patterns: adapter layer (normalize external APIs to internal interfaces), retry with exponential backoff, circuit breakers for degraded external services, webhook receivers for async callbacks, idempotency keys to prevent duplicate operations on retry.

AI-Native Development

The JD lists "AI-Native: Familiar with latest agentic and coding technologies, trusts but verifies model outputs" as a desired qualification. This is a cultural signal more than a technical requirement.

What "AI-native" means at a startup this size

  • Coding with AI tooling: Cursor, Copilot, Claude Code as daily drivers. The expectation is that you use these fluently to move faster, not that you're building AI features.
  • "Trusts but verifies": they want engineers who leverage AI output without rubber-stamping it. Generate code, review it critically, ship what's correct. The emphasis on "well-tested code" in the responsibilities section pairs with this: AI generates, tests validate, human judges.
  • Potential AI features: document understanding (parsing existing legal documents to extract obligations), automated form filling (generating state-specific filings from structured data), classification (determining which dissolution path applies based on entity characteristics). These are plausible product directions, though the JD doesn't specify them.

Testing Web Applications

Automated test suites at multiple layers:

  • Unit tests: isolated function/module tests, typically with Jest, Vitest, or pytest. Mock external dependencies, assert return values and side effects.
  • Integration tests: verify that multiple modules work together correctly. Database queries return expected rows, API routes return expected responses, middleware chains execute in order. May use test databases or in-memory stores.
  • End-to-end (E2E) tests: Playwright, Cypress, or Selenium driving a real browser against a running app. Assert that user flows (click button, fill form, see result) work as expected.
  • Regression tests: tests written specifically to prove a fixed bug stays fixed. You write a test that reproduces the broken behavior, verify it fails, apply the fix, verify it passes. The test stays in the suite permanently as a guardrail.
  • Contract tests: verify that boundaries between components (API shapes, function signatures, state machines) stay consistent. If module A depends on module B's output shape, a contract test breaks when B changes without A being updated.

Event-Driven Systems

Architectures where components communicate through events rather than direct calls. The key distinction from request/response:

  • Pub/sub: a component publishes an event ("order.placed"), zero or more subscribers react independently. The publisher doesn't know or care who's listening. Technologies: Redis Pub/Sub, AWS SNS/SQS, Google Pub/Sub, RabbitMQ, NATS.
  • Event sourcing: instead of storing current state, store a log of every state change as an immutable event. Current state is derived by replaying events. Common in financial systems, booking systems, anything where audit trail matters.
  • CQRS (Command Query Responsibility Segregation): separate the write model (commands that emit events) from the read model (projections built by consuming events). Lets you optimize reads and writes independently.
  • Reactive streams / backpressure: RxJS, Node.js streams, async generators/iterators. Data flows through a pipeline of transformations, with backpressure so fast producers don't overwhelm slow consumers. Generators (function*) and async generators (async function*) are one implementation pattern here, where yield produces values on demand rather than eagerly.
  • WebSockets / SSE: persistent connections where the server pushes events to the client as they happen rather than the client polling.
  • Event loops / message queues: decoupling work from the request lifecycle. A booking request enqueues a job; a worker picks it up, processes it, emits completion events that trigger downstream steps (send confirmation email, update availability, notify advisor).

In travel tech specifically

A booking triggers a chain of downstream events (payment capture, inventory hold, confirmation email, advisor notification, calendar sync), each handled by independent consumers. The system needs to handle failures at any step (what if payment succeeds but email fails?) without corrupting state. That's saga/choreography pattern territory.

Relational Databases and ORMs

  • Relational DB fluency: schema design (normalization, denormalization tradeoffs), indexing strategy (covering indexes, composite indexes, partial indexes), query optimization (explain plans, N+1 detection, join strategies), migrations (zero-downtime schema changes, backfills on large tables), transactions and isolation levels (read committed vs serializable, when each matters).
  • ORMs: Sequelize, Prisma, TypeORM, Drizzle (JS ecosystem); SQLAlchemy, Django ORM (Python). The practical question is whether you can reason about what SQL the ORM generates, recognize when it's doing something pathological, and drop to raw queries when the abstraction leaks.

Stateful Web Applications / Complex Workflows

  • Stateful: the app tracks multi-step processes that span multiple requests and potentially days. A booking isn't a single form submission; it's: search, select, hold inventory, collect passenger details, payment, confirmation, post-booking modifications. Each step depends on the previous state, and the system needs to handle interruptions, timeouts, concurrent modifications, and partial failures.
  • State machines: explicitly modeling valid transitions (draft → pending_payment → confirmed → modified → cancelled). Prevents invalid states (you can't modify a cancelled booking). Libraries like XState formalize this; many teams do it ad-hoc with status columns and conditional logic.
  • Optimistic locking / concurrency: two advisors booking the last seat simultaneously. How does the system resolve that? Optimistic locking (version columns), pessimistic locking (SELECT FOR UPDATE), or inventory holds with TTLs.
  • Complex workflows: multi-party coordination (traveler, advisor, airline/hotel API, payment processor), each with its own failure modes and retry semantics. Saga pattern (compensating transactions) vs. orchestration (a central coordinator) vs. choreography (each service reacts to events).

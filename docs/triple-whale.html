Triple Whale: Growth Engineer Prep

Analytics, Flags, Warehouses, and How They Connect

A growth engineer instruments a product, runs experiments on it, and measures what converts. The tooling for that breaks into five categories. They're often bundled (PostHog alone covers three of them), but they do different things.

CDP
Customer Data Platform		 Collects events from every source (web app, mobile, backend, third-party APIs), unifies identity across devices/sessions, and routes that unified stream to downstream destinations. The CDP doesn't analyze anything; it's a switchboard. Segment, mParticle, RudderStack, Jitsu
Product analytics Answers "what are users doing?" Funnels, retention curves, cohort analysis. Takes the event stream (often from the CDP) and makes it queryable without SQL. PostHog, Amplitude, Mixpanel, Heap

The canonical pattern: instrument once via the CDP's SDK (segment.track()), and the CDP replicates that event to every downstream tool. Swap Amplitude for Mixpanel? Change a toggle in Segment; don't touch your code.

PostHog's position is unusual. It spans product analytics, session recording, feature flags, and experiments in one tool. Companies that use PostHog as their primary analytics often skip the CDP entirely because PostHog is already receiving all the events directly. This is TW's situation: PostHog gets events directly from the app, no CDP in between.

The tradeoff: without a CDP, events only go to PostHog. If you want the same events in BigQuery, HubSpot, and ad platforms, you either instrument each destination separately or build a custom fan-out. That's what Google Tag Manager (GTM) partially handles for TW's ad pixels, but it's not a unified approach.

Experimentation

Tools the JD mentions vs what's running

The JD lists LaunchDarkly, Statsig, and Optimizely as examples, then adds "or building lightweight equivalents when needed."

  • LaunchDarkly is a feature flag delivery service. You define flags and targeting rules in their dashboard, and their SDK evaluates them client-side or server-side. It's good at flag delivery and percentage rollouts but doesn't have built-in experiment analysis; you pair it with a separate analytics tool to measure results.
  • Statsig (built by ex-Facebook engineers) covers the full experiment lifecycle: flags, A/B assignment, and statistical analysis in one product. It auto-calculates significance and handles mutual exclusion between experiments. Closer to what a growth team actually needs than a pure flag service.
  • PostHog covers flags, experiments, and analytics together. TW already has it loaded, and it already knows about their users and shops. Its experiment feature flags are empty, meaning nobody has created experiments yet, but the SDK and analytics pipeline are already wired up. Starting here avoids adding a new vendor and a new SDK.

Where Statsig would help (and PostHog doesn't)

Three concrete gaps in PostHog's experiment system that Statsig handles natively:

  1. Sequential testing. PostHog uses fixed-horizon analysis: you pick a sample size, wait until it fills, then read results. Peeking early inflates false positives. Statsig uses sequential testing (always-valid p-values), so you can monitor results continuously without statistical penalty. For a growth team shipping weekly, this matters.
  2. Mutual exclusion layers. If two experiments run on the same user population and affect the same metric, their results confound each other. PostHog has no native mechanism to prevent overlap. Statsig lets you define exclusion layers: experiments in the same layer are mutually exclusive, experiments in different layers run independently.
  3. Guardrail metrics. PostHog tracks one primary metric per experiment. Statsig lets you define guardrail metrics (e.g., "don't tank session duration while optimizing upgrade rate") and auto-flags when a winning variant harms a secondary metric.

PostHog is the right starting point because the SDK is already loaded and the analytics data is already there. Statsig becomes worth adding when the experiment volume is high enough that overlap and continuous monitoring become real problems.

Three layers of flags

  1. Plan gating (tw-features): deterministic. If your plan includes "PIXEL", you get Pixel features. No randomization. This is billing logic.
  2. Infrastructure routing (tw-global-config): operational. Routes queries to ClickHouse shards. Not user-facing.
  3. Experiments (PostHog): probabilistic. A/B tests on upgrade copy, onboarding flows, gate types. Currently empty. This is what the role builds.

PostHog has $enabled_feature_flags and $feature_flag_payloads in localStorage, both empty. The infrastructure exists; nobody has activated it.

Experiments layer on top of plan gating. You don't experiment with whether a user gets multi-touch attribution (that's a plan entitlement). You experiment with how you present the upgrade.

Consistent hashing: PostHog uses MurmurHash on distinct_id + flag_key (user ID plus flag name) to assign variants deterministically. Same user, same variant, no DB lookup. With shop-level groups, it hashes shop_id + flag_key instead.

React integration

PostHog's React SDK (posthog-js/react) provides a PostHogProvider that wraps the app at the root. It initializes the PostHog client once and makes it available via context. Two interaction points follow from that.

Flag evaluation uses hooks, not effects. The PostHog client fetches all flag assignments on init (a single /decide call) and caches them in memory. Hooks like useFeatureFlagVariantKey read from that cache synchronously. No network request per render. If flags haven't loaded yet, the hook returns undefined and you render a default.

function AttributionPanel() {
  const variant = useFeatureFlagVariantKey('attribution-gate-style')

  if (variant === 'blurred-preview') {
    return <BlurredPreview onUpgrade={handleUpgrade} />
  }
  return <HardGate onUpgrade={handleUpgrade} />
}

Event capture goes in handlers, not effects. Call usePostHog() to get the client, then posthog.capture() in click handlers, form submissions, and callbacks.

function HardGate({ onUpgrade }) {
  const posthog = usePostHog()

  const handleClick = () => {
    posthog.capture('upgrade_cta_clicked', {
      gate_type: 'hard',
      feature: 'multi_touch_attribution',
      plan: 'Free'
    })
    onUpgrade()
  }

  return <button onClick={handleClick}>Upgrade to unlock</button>
}

What the experiment creation step looks like

A growth engineer creates an experiment in PostHog's UI, not in code. They define: a feature flag name (attribution-gate-style), variants (hard-gate vs blurred-preview), targeting rules (Free plan only, or pql_score >= 60), and the conversion event (plan_upgraded). The frontend code that checks useFeatureFlagVariantKey('attribution-gate-style') already exists at that point. PostHog handles assignment, exposure tracking, and statistical analysis. After enough data accumulates (usually 1-2 weeks), the results page shows conversion rates per variant with confidence intervals, and a human decides to ship the winner or iterate.

Schema enforcement

Analytics events break silently. Someone renames trigger_type to triggerType in a refactor, and a month of funnel data becomes unjoinable because the old events and new events have different property names. PostHog won't reject the event; it'll just show up as a new property. A TypeScript event map catches this at compile time by constraining both event names and their properties to a fixed contract:

interface GrowthEvents {
  gate_shown: {
    feature: string
    gate_type: 'hard' | 'blurred_preview' | 'contextual_nudge' | 'data_anchored'
    user_plan: string
    experiment_variant?: string
  }
  plan_upgraded: {
    from_plan: string
    to_plan: string
    monthly_price: number
    trigger: string
  }
}

function capture<K extends keyof GrowthEvents>(
  event: K, props: GrowthEvents[K]
) {
  posthog.capture(event, props)
}

PQL Scoring

A PQL (Product Qualified Lead) score quantifies how ready a free-tier user is to convert, based on in-product behavior. The growth engineer builds the system that computes it, stores it, and triggers actions when thresholds are crossed.

The force_upgrade_* fields on tw-subscription show that a rudimentary scoring system already exists on the backend, but it's hardcoded. The growth engineer replaces it with a data-driven, experiment-ready version.

Scoring function

function computePqlScore(shop, subscription, userActivity) {
  if (subscription.contract_type !== 'Free') return null
  if (subscription.force_upgrade) return 100

  let score = 0

  // Moby is hard-gated on Free; repeated gate views signal intent
  if (userActivity.mobyGateViews7d >= 5) score += 30
  else if (userActivity.mobyGateViews7d >= 2) score += 15

  const platforms = shop.mspConnected || 0
  if (platforms >= 3) score += 15
  else if (platforms >= 1) score += 5

  if (shop.pixel_install_status === 'installed') score += 5
  if (shop.welcomeWizardData?.completed) score += 5

  if (userActivity.loginDays7d >= 5) score += 10
  if (userActivity.teamInvites >= 2) score += 10
  if (userActivity.gatedFeatureViews7d >= 3) score += 10

  return Math.min(score, 100)
}

What the engineering actually looks like

This is a Node.js service with a database, a scheduled job, and a REST API. The day-to-day is writing the SQL that aggregates user behavior, the function that turns aggregates into a score, the API that serves it, and the React component that checks it before rendering an upgrade prompt.

1. Schema

A table (in MongoDB, since that's where TW's user/shop records already live, or in ClickHouse alongside the event data) storing the computed score per shop:

// shop_pql_scores collection
{
  shop_id: "shop_abc123",
  score: 75,
  signals: {
    moby_gate_views_7d: 5,
    platforms_connected: 4,
    login_days_7d: 6,
    gate_views_7d: 8,
    force_upgrade: false,
    pixel_installed: true
  },
  computed_at: "2026-08-14T02:00:00Z",
  plan: "Free"
}

2. Scheduled job

A cron or BullMQ job that runs hourly. For each free-tier shop, it queries ClickHouse for that shop's activity over the last 7 days, applies the scoring function from above, and writes the result:

SELECT
  shop_id,
  countIf(event = 'gate_shown') AS gate_views_7d,
  countIf(event = 'gate_shown' AND properties.feature = 'moby') AS moby_gate_views_7d,
  uniqExact(toDate(timestamp)) AS login_days_7d
FROM posthog_events
WHERE timestamp >= now() - INTERVAL 7 DAY
GROUP BY shop_id

The scoring function (shown above) combines these ClickHouse aggregates with data from the shop and subscription records that are already in MongoDB. High-weight events like repeated Moby gate views could also trigger an immediate rescore outside the hourly cycle.

3. REST API

// GET /api/growth/pql/:shopId
// Returns the current score and the signals that contributed to it
{
  score: 75,
  signals: { moby_gate_views_7d: 5, platforms_connected: 4, ... },
  threshold_actions: {
    show_upgrade_prompt: true,   // score >= 80
    enroll_in_experiment: true,  // score >= 60
    notify_sales: false          // score >= 90
  }
}

4. Frontend consumption

The React app calls this endpoint and uses the score to decide what to render. If the score is above 60, PostHog enrolls the user in an upgrade experiment. If above 80, the app shows an upgrade prompt directly. If above 90, the backend also sends a lead to HubSpot (which TW already uses for sales).

5. PostHog sync

After computing a score, push it as a user/group property to PostHog. This enables experiment targeting within PostHog's UI: create a feature flag that only activates for users with pql_score >= 60, without writing any targeting logic in the app code.

The iterative part

Product decides "users who connect 3+ ad platforms are more likely to upgrade." You write the ClickHouse query that counts platforms per shop, add it as a signal in the scoring function, deploy, and watch whether the score correlates with actual conversions over the next two weeks. If it does, increase the weight. If not, remove it. The weights start from intuition and get tuned by data.

function GatedFeature({ featureKey, children }) {

Moby

Moby is TW's AI layer (chat, creative gen, automations). The growth engineer doesn't build Moby's core but owns the conversion surfaces around it.

Moby 2 is hard-gated on Free

The free plan dashboard shows "Moby 2 — Available on Paid Plans — Upgrade." No credit meter, no trial allowance, just a gate. The pricing page lists "Moby Chat to search the web or knowledge base" for the free tier, but the full Moby 2 (analytics, agents, creative gen) requires a paid plan. TW doesn't publish specific credit amounts for any tier; paid plans say "Use Moby Daily" / "Run Moby at Scale."

The default route for a free plan account is /chat (Moby). Users land directly on the thing they can't use. That makes the Moby gate the highest-traffic upgrade surface.

Growth surfaces (free→paid)

The primary upgrade lever isn't Moby. It's the attribution model ceiling.

A. Attribution value gap (primary)

Free users see first/last-click attribution. As their ad spend and channel mix grow, single-touch becomes visibly wrong: last-click credits the final touchpoint and ignores the awareness campaign that started the journey. The gap between what they see and what multi-touch would show them is a natural upgrade trigger. The experiment variable is how you surface that gap: blurred multi-touch preview, side-by-side comparison, or a percentage-delta callout anchored to the merchant's own data.

B. Moby trial (secondary)

Give free users 3 days of Moby access. Accounts are tied to real Shopify domains, preventing throwaway signups. A cheaper model (Luna) could serve the trial at lower marginal cost. The growth engineer instruments the trial, measures conversion to Foundation within 7/14/30 days, and A/B tests trial duration (3 vs 5 vs 7 days).

C. Sonar contextual upsell (tertiary)

When a Free user views attribution data showing Klaviyo as a channel, surface a Mantine drawer: "You have 200 identified visitors who didn't buy. Sonar pushes these to Klaviyo automatically." Contextual, data-grounded, specific to the merchant's store. Gated on a PostHog flag, no external in-app messaging tool needed.

Option A is the strongest because it's organic: the gap emerges naturally from the merchant's own growth. No artificial wall needed. Options B and C are testable supplements.

Sonar: first-party data activation

TW's Triple Pixel identifies visitors via a first-party identity graph, resolving anonymous browsers to known profiles even before they give an email. Sonar pushes that identity data to external platforms.

Sonar Send (for shops → Klaviyo)

Pushes identity-resolved visitor profiles to Klaviyo. Without Sonar, Klaviyo only reaches people who explicitly gave their email (newsletter signup, started checkout). With Sonar, Klaviyo can fire browse-abandonment flows to visitors who were identified by the pixel but never gave their email. Grows Klaviyo's addressable audience substantially.

Sonar Optimize (for ad platforms)

Builds first-party audience segments (e.g., "high-LTV repeat buyers, no purchase in 60 days") and syncs them to Meta, Google, and TikTok as Custom Audiences for lookalike targeting or retargeting. Without Sonar, Meta only knows what its own pixel observed. With Sonar, Meta gets TW's richer, cross-channel view of the customer.

The dashboard lists both under one Foundation feature: "First-party data activation: Meta, Google, TikTok, Klaviyo." The marketing page splits them across tiers, but the dashboard doesn't.

Compass: MMM and incrementality

$4,800/mo add-on, not a plan tier feature. Compass is a managed data science service: Bayesian marketing mix models that decompose total revenue into per-channel incremental contributions, with train/test evaluation splits, saturation curves per channel, marginal lift analysis, and GeoLift incrementality testing (randomized geographic holdout experiments that require pausing real ad spend in test regions). Backed by a dedicated Marketing Data Science Team. 7+ internal ClickHouse tables power the system. This is irrelevant to growth engineering but worth knowing exists.

The differentiator

Attribution is the foundation, but every competitor does attribution. TW's differentiator is being both the analytics layer and the execution layer: Moby takes actions in ad accounts (pause ads, adjust budgets, generate creative). Whether that claim holds depends on Moby adoption, which is why AI growth surfaces (the Moby gate, upgrade prompts, onboarding into paid AI features) are central to this role.

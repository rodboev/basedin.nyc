MVC for React Developers

Architecture patterns you already use, named and mapped to interview vocabulary. Grounded in Next.js, the Liberty scheduling engine, and the Gen Digital code challenge.

Sections

You already do this

MVC isn't a framework or a library. It's a name for keeping three concerns in separate places: where data comes from, how it looks on screen, and what happens when the user does something. If your React components don't query databases and your SQL queries don't return JSX, you're already doing it.

The scheduling engine at Liberty has a SQL connection pool in lib/db.js, route handlers that run queries and return JSON, and React components that render calendars. Those are the three layers. You wired them up that way because mixing them would've been a mess, not because someone told you it was called MVC.

The Gen Digital code challenge is the same story. filterArtworks is a pure function that operates on data. artFetcher handles HTTP. The page component orchestrates fetching and state transitions. The card components render artwork. Each piece does one thing.

When an interviewer asks "do you know MVC?" they're asking whether you think about these boundaries deliberately. You do. Now you have the vocabulary for it.

The three layers

Model

The Model is everything about data: where it's stored, how you get it, what rules apply to it, and how it's shaped. Business logic lives here. Validation lives here. Database queries, API calls to third-party services, calculations, filtering, sorting, transformation of raw records into something the rest of the app can use.

The defining characteristic: the Model has no idea it's part of a web app. It doesn't know about HTTP requests, HTML, React, or what the URL looks like. You could call a Model function from a CLI script, a cron job, or a test, and it would work the same way.

In JavaScript terms, a Model is a plain function or class that takes data in, does something with it, and returns data out. No req/res objects, no JSX, no useState.

View

The View is what the user sees. In React, that's your components. They receive data as props, render it, and report user interactions back up. A well-behaved View doesn't fetch data, doesn't run business logic, doesn't decide what's valid. It renders what it's given.

This is the layer React devs understand intuitively. A <ServiceCard service={service} /> that renders a technician's name, a schedule, and a map pin is pure View. If you handed it different data, it'd render different content. It has no opinions about where the data came from.

Controller

The Controller is the middleman. It receives a request (an HTTP request, a user action, a page load), decides which Model functions to call, and hands the results to the View. It's the wiring layer.

This is the one that feels least natural in React, because React components often do all three jobs at once. A component that fetches data in useEffect, filters it, and renders the result is acting as Model, View, and Controller simultaneously. MVC says: split those into separate pieces.

In Next.js, the Controller layer maps to several constructs (covered in the next section). The key idea: the Controller knows about both the Model and the View, but they don't know about each other.

Why the separation matters

At one developer, mixing layers feels faster. You can hold the whole thing in your head. At a team, mixed layers become expensive:

  • Testing: if your offer-eligibility rules are inside a React component, you need to mount the component, mock the DOM, and render to test them. If they're in a plain function, you call the function with test data and check the output. The scheduling engine's gap-packing algorithm runs in a Worker thread precisely because it's pure computation, decoupled from everything else.
  • Reuse: if two different pages need the same business logic (say, an offer comparison page and a checkout page both need rate calculations), and that logic lives inside a component, you're either duplicating it or extracting it into a shared component that exists only for the logic. A Model function can be called from anywhere.
  • Compliance: in fintech, regulators can ask for evidence that rate display logic is correct. "Here's the function, here are the 40 tests" is a cleaner answer than "it's computed inline in the JSX of the OfferCard component."
  • AI-generated code: when AI scaffolds a component that fetches, transforms, and renders in one place, the review surface is the entire component. When the layers are separate, you can review the business logic independently of the rendering.

Next.js is MVC

Next.js, especially with the App Router, gives you constructs that map to all three layers. It doesn't enforce the separation, but it provides the slots.

Model layer in Next.js

Plain TypeScript/JavaScript modules, typically in lib/, services/, or models/ directories. No Next.js-specific imports. These are the files that talk to your database (Prisma, Drizzle, raw SQL), call external APIs, validate input (Zod, Pydantic-style), and contain business rules.

// lib/offers.ts — Model layer
export async function getPersonalizedOffers(userId: string, creditScore: number) {
  const eligible = await db.offers.findMany({
    where: { minCreditScore: { lte: creditScore } }
  })
  return eligible.map(offer => ({
    ...offer,
    monthlyPayment: calculatePayment(offer.apr, offer.term, offer.amount)
  }))
}

export function calculatePayment(apr: number, termMonths: number, principal: number) {
  const monthlyRate = apr / 100 / 12
  return (principal * monthlyRate) / (1 - Math.pow(1 + monthlyRate, -termMonths))
}

calculatePayment is the clearest Model function: pure math, no framework, independently testable. getPersonalizedOffers has a database dependency but still has no knowledge of HTTP or React.

Controller layer in Next.js

Four constructs fill this role:

ConstructRoleWhen to use
Server Components (default in App Router)Page controllers. They run on the server, call Model functions, pass data as props to View components.Initial page loads, data that's known at request time.
Route Handlers (route.ts)API controllers. REST-style endpoints that receive HTTP requests, call Model functions, return JSON.Client-side fetches after initial load, webhooks, third-party callbacks.
Server Actions ('use server')Mutation controllers. Functions that handle form submissions and state changes.Any write operation: submitting an application, updating preferences, saving a draft.
Middleware (middleware.ts)Cross-cutting controller. Runs before every request.Auth redirects, A/B bucketing, geo-routing, header injection.

A Server Component acting as a controller:

// app/offers/page.tsx — Controller layer (Server Component)
import { getPersonalizedOffers } from '@/lib/offers'
import { OfferList } from '@/components/OfferList'
import { getSession } from '@/lib/auth'

export default async function OffersPage() {
  const session = await getSession()
  const offers = await getPersonalizedOffers(session.userId, session.creditScore)
  return <OfferList offers={offers} />
}

Three lines: authenticate, fetch, render. The page component has no business logic, no database queries, no JSX beyond handing data to a View component.

View layer in Next.js

Client components ('use client') that receive props and render UI. Design system primitives (Reshaped, Radix, shadcn). Anything that calls useState, useEffect, or handles browser events.

// components/OfferList.tsx — View layer
'use client'

export function OfferList({ offers }: { offers: Offer[] }) {
  return (
    <div className="offer-grid">
      {offers.map(offer => (
        <OfferCard key={offer.id} offer={offer} />
      ))}
    </div>
  )
}

The View doesn't know where the offers came from. Database? Cache? Hardcoded test fixture? Doesn't matter. Same props, same output.

Where the line blurs

Client components that fetch data are acting as both Controller and View. This is common and not always wrong, but it's where bugs hide. The gen-digital code challenge's Search component is a Controller-View hybrid: it manages the fetch lifecycle (Controller) and renders the search input and results (View). The filterArtworks extraction pulled the Model logic out of that hybrid, which is why 16 tests cover the filtering without mounting a single component.

The pragmatic rule: if a function could be useful outside of React (in a test, a script, a server action, a different page), it belongs in the Model layer. If it's wired to a specific request/response cycle, it's Controller. If it renders pixels, it's View.

Where your code diverges from strict MVC

Notes-AI: the same instinct, more moving parts

The pattern both projects share

In both the scheduling engine and notes-ai, the route handlers are doing too much. They're the Controller (receive request, return response) and also a chunk of the Model (SQL building, data transformation, business rules). This is the most common way MVC blurs in Next.js codebases, and it's the thing a team like Gen Engine's would formalize.

In strict MVC, you'd extract the business logic into service modules:

What you haveWhat strict MVC looks like
api/notes/route.js builds SQL, transforms records, fingerprints them, writes to three storage tiers, and returns the response. A services/notes.ts owns the query, transformation, and fingerprinting. A services/noteCache.ts owns the three-tier read-through. The route handler calls both and returns the result.
api/emails/route.js expands prompts, streams from OpenAI, parses chunks, groups batches, and manages caching. 300 lines. A services/emailGenerator.ts owns prompt expansion and OpenAI streaming. A services/emailCache.ts owns cache coordination. The route handler wires them together and returns a stream. Maybe 30 lines.
api/schedule/route.js receives date range, runs the scheduling algorithm in a Worker, and returns JSON. Already close. The Worker thread is a natural service boundary. The route handler is thinner here because the heavy logic lives in the Worker.

The scheduling engine is actually closer to MVC than notes-ai, because the Worker thread forced a separation. When the computation is expensive enough to need its own thread, you've already extracted the Model. Notes-ai doesn't have that forcing function: the OpenAI call is I/O-bound, not CPU-bound, so there's no performance reason to pull it out of the route handler. The architectural reason still applies, though.

The hook problem

Both projects also put business logic in React hooks. useSchedule batches results (100 at a time), transforms API responses into calendar events, and manages progress state. useEmails parses streaming JSON, merges partial results, and handles EventSource lifecycle.

In MVC terms, these hooks are client-side Controllers that also contain Model logic. The View components are clean (they receive props and render), but the hooks are doing data transformation that could live in a utility module.

The practical test: could you call the batching logic or the streaming parser from a different context (a test, a CLI tool, a different component) without importing React? If not, the business logic is coupled to the hook lifecycle.

This is worth naming because it's the exact pattern the Gen Digital code challenge addressed. filterArtworks was extracted from the component into a pure function, making it testable without React. The same extraction would apply to the streaming JSON parser in useEmails or the calendar-event transformation in useSchedule.

Where you're clean, where you're not

  • Clean: data access modules (db.js, supabaseHelper.js, diskStorage.js) are genuine Model code with no framework awareness. Components are genuine Views. The overall data flow (component → hook → API route → storage) follows the right direction.
  • Not clean: route handlers mix Controller and Model responsibilities. Hooks mix Controller and Model responsibilities. There's no services/ or lib/ layer between "receive the HTTP request" and "talk to the database / call OpenAI." The wiring logic and the business logic live in the same functions.
  • Incidentally right: the scheduling engine's Worker thread is the closest thing to a proper service layer in either project, and it exists for performance, not architecture. The separation is real, but it was a side effect of needing a separate thread, not a deliberate MVC choice.

None of this means the code is wrong. Both projects work and ship. The point is recognizing where the seams are so that when an interviewer asks about MVC, you can say: "I've built this way, and I know where the extraction points are when the codebase grows."

Neighboring patterns

MVC is the oldest and most widely referenced of these patterns (1979, Smalltalk). In interviews, people sometimes use these terms interchangeably or ask how they differ. Here's the minimum you need to recognize each one and nod along.

PatternKey ideaWhere you've seen it
MVC Model holds data/logic. View renders. Controller handles input and mediates. Next.js App Router, Rails, Django, ASP.NET, Spring. What Jerome's team uses.
MVVM Model-View-ViewModel. The ViewModel is a data-binding layer between the Model and the View. The View "observes" the ViewModel and updates automatically when it changes. Angular (two-way data binding), Vue (reactive refs), SwiftUI, WPF. React with MobX is MVVM-flavored. A Zustand store that a component subscribes to is acting as a ViewModel.
MVP Model-View-Presenter. The Presenter explicitly tells the View what to render (no data binding). The View is completely passive. Android (before Jetpack Compose), older Java GUIs. Less common in web dev.
Clean Architecture Dependencies point inward. Business rules at the center, frameworks at the edges. A stricter version of MVC's idea: the Model shouldn't import the Controller, and the Controller shouldn't import the View framework. Enterprise Java, Go services. When someone says "hexagonal architecture" or "ports and adapters," it's the same family. Overkill for most frontend code, but the principle (business logic doesn't depend on framework code) is always sound.
Flux / Redux Unidirectional data flow: Action → Dispatcher → Store → View. A reaction to MVC's bidirectional wiring getting tangled in complex UIs. React + Redux, Zustand, Jotai. You've used this pattern without the label if you've used useReducer: dispatch an action, the reducer returns new state, the component re-renders.

The common thread: all of these are strategies for keeping business logic, presentation, and orchestration from bleeding into each other. They differ in how they wire the three concerns together (callbacks, data binding, unidirectional flow) and how strict they are about it. In a React/Next.js codebase, you'll naturally blend MVC (server components as controllers, route handlers as API controllers) with Flux-like patterns (client-side state management). That's normal. Nobody implements pure MVC in a React app.

Interview vocabulary

Terms that show up alongside MVC in architecture conversations. Each one is something you already practice; this is the label and the one-line definition so you can respond without hesitating.

TermWhat it meansYour example
Separation of concerns Each module does one thing. The umbrella principle behind MVC. filterArtworks doesn't fetch. artFetcher doesn't filter. Components don't query SQL.
Single responsibility A class or function has one reason to change. From SOLID (the S). The generation counter has one job: tracking request identity. The score threshold has one job: filtering noise. Changing either doesn't affect the other.
Dependency injection Pass dependencies in rather than importing or constructing them internally. filterArtworks(artworks, query, threshold) receives its data as arguments. The 16 tests pass hand-crafted arrays; no API mock needed.
Pure function Same input, same output, no side effects. Deterministic and testable. filterArtworks and calculatePayment. No network calls, no state mutation, no randomness.
Immutability Don't modify existing data; create new copies with changes. [...data].sort() instead of data.sort(). Spread-and-set instead of object mutation.
Referential equality Comparing identity (===) rather than deep comparing contents. How React detects change. The sort() bug: same reference after mutation, React skips the re-render.
Discriminated union A type where one field (the "discriminant") determines which other fields exist. Makes invalid states unrepresentable. The Status type: 'idle' | 'loading' | 'success' | 'error' replaces boolean flags that could desync.
Data transfer object (DTO) A plain object that carries data between layers. No behavior, just shape. The structured objects that serviceSetups/route.js returns after transforming raw SQL records. The API response is a DTO; the component receives it and renders it.
Service layer A module that encapsulates business logic and is called by controllers. The Model's public API. artFetcher is a service: it owns URL construction, caching, abort handling. The component calls it without knowing those details.
Hydration The browser attaching event handlers to server-rendered HTML so it becomes interactive. SSR delivers visible content fast; hydration makes it clickable. The gap between "I can see the offer" and "I can click Apply" is the hydration window.

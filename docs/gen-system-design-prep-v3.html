Reasoning Framework: Driving An Ambiguous Prompt

In an AI-augmented senior role, your job is to impose enough structure on an ambiguous problem that whoever writes the code can't get it subtly wrong. Each move below signals "Here's the discipline that stops things breaking."

Run these five moves, in order, on any vague prompt. They work on the offer list, the attribution flow, a design-system component, anything.

  1. Clarify and slice. Cut the problem into independent pieces and ask which one they want.
  2. Name the trust boundary. Who's untrusted, what can they reach, where's the guard.
  3. Draw the state grid. States by events, every cell filled.
  4. Locate the policy. What's the one rule with one owner, what's mechanics you can duplicate.
  5. State the proof. How you'd verify each claim, and what your verification can't reach.

Move 1: Decompose into independent slices

Don't start designing the whole marketplace. Say: "there are several independent surfaces here; each ships and breaks on its own. Which do you want me to go deep on?" That move shows you decompose and hands the ambiguity back as a clarifying question instead of a guess.

What makes each slice independent:

  • Distinct mechanism: each solves a different problem.
  • Independently reviewable: you can read one without the others open.
  • Order-independent or explicitly stacked: the form doesn't need offers to exist first.
  • Non-overlapping code: they touch different files, so two people build them without colliding.
  • Fails in isolation: a bug in sort doesn't corrupt the form.

How the loan funnel decomposes, with the layers each slice owns:

Input form (the wizard). Collects applicant data across steps.
  • Layers: form-state management (react-hook-form), client validation (zod), input masking, per-step server-validation POST, session persistence, accessibility.
  • Independent because it owns its own step state machine and validation; give it nothing but a submit endpoint and it works, with no knowledge of offers or attribution.
Offer fetch and render. Get offers, show cards, sort and filter, handle every fetch state.
  • Layers: data fetching (React Query/SWR), the discriminated-union state machine, derived state (sort and filter as pure functions), list rendering with stable keys, virtualization, loading/empty/error UI, resilience (AbortController, partial results, stale-while-revalidate).
  • Independent because it's a read surface over an API; point it at a mock offers endpoint and it renders with no form and no attribution present.
Attribution capture. Capture source params, persist them, re-inject to the outbound handoff.
  • Layers: URL parsing (URLSearchParams whitelist), persistence (httpOnly cookie plus localStorage fallback), link decoration, Referrer-Policy awareness, server lead-id minting.
  • Independent because it's a cross-cutting carry-through with its own capture/persist/re-inject lifecycle; test it by checking params survive navigation, regardless of the form or offers.
Apply / approval handoff. The outbound redirect to a lender with attribution attached, and the return.
  • Layers: URL decoration (decorateUrl), the trust boundary (applicant PII stays out of the URL, only identifiers ride it), redirect handling, return-state handling.
  • Independent because it's the exit: it consumes an offer id plus attribution and produces a redirect, indifferent to how offers were fetched or how the form collected data.
Telemetry / event collection. Fire events for clicks and page views with dedup, batch, retry.
  • Layers: event envelope (event_id, occurred_at), batching, sendBeacon on unload, retry with backoff, sampling.
  • Independent because it observes the others while none depend on it; rip it out and the funnel still works.
Session management. Identity across requests, and what happens when it expires mid-flow.
  • Layers: httpOnly session cookie, idle and absolute timeout, 401 detection, keep-alive warning.
  • Independent because it wraps the whole flow but has its own lifecycle; every other slice just assumes a session id is present.

Move 2: Name the trust boundary

Whenever PII or auth appears, recite three fields. This is the crisp structure behind the storage and validation rules you already know.

  • Untrusted principal: who crosses the boundary. For a web form it's the browser, meaning the user and anything running in their page.
  • Reachable surface: the endpoint or code path that principal can hit. The submit API.
  • Enforcement point: the narrowest guard that blocks bad input, not a broad middleware that also blocks legitimate routes. Server-side validation and authorization at that endpoint.

Said out loud for the loan form: "The client zod schema is UX; the server schema is the trust boundary. The client's check is a convenience, the server's is the authority. SSN never rides in a URL, because the query string lands in logs and Referer headers." That last clause pre-empts the follow-up.

Authentication is not authorization. "Is this a valid logged-in user" is a different check from "is this user allowed to touch this specific object." The cross-user row is the classic gap: auth passes, authz was never checked. That's IDOR.

The enforcement point has to be narrow and low. A guard that's too broad blocks legitimate traffic. A guard that's too high, like hiding a button or a client-side route guard, is cosmetic, because the principal reaches the surface directly with curl. Real enforcement sits at the surface the principal actually hits, which is the server, not the UI.

Move 3: Draw the state grid

A state machine narrated in prose hides transitions; a grid forces every one into view. On a whiteboard, put states down the side and events across the top, then fill every cell with the resulting state. The cell you can't fill is the bug you'd have shipped.

  • States (rows): idle, loading, loaded-empty, loaded-partial, error, stale-revalidating.
  • Events (columns): fetch-start, success, failure, user-edits-input, timeout.
  • Every cell names the target state. "success" from "loading" with zero rows lands in loaded-empty, a real state that shows "no offers match," not an error.

This is the discriminated union from the Offer List section, made visible. Doing it on the board is a top-decile move because filling cells surfaces gaps that talking never would.

Move 4: Locate the policy (centralize policy, duplicate mechanics)

Ask "where does this rule live?" The rule of thumb: one logical rule gets one owner; the mechanical work of applying it can be copied freely.

  • Policy is the decision. "What counts as a valid, showable offer" (fields present, not expired, user eligible) gets a single owner: one isEligible(offer) predicate.
  • Mechanics is the application. The card that renders an offer is mechanics; several card variants are fine.
  • The trigger to extract: when the same rule appears in 3+ places (the list filter, the sort, the apply button), that's three drift sites. Extract to one predicate so there's one thing to change and one thing to test.
  • The other trigger: a rule from a specific layer (a lender's quirk, a transport detail) leaking up into shared code. Keep backend-specific policy out of the generic layer.

Naming the policy/mechanics split unprompted is a strong senior signal. "If I'm patching the same eligibility check in four places, I'm not fixing a bug, I'm postponing three."

Move 5: State the proof (prove, don't assert) and shape the tests

When you propose something, immediately say how you'd verify it, and volunteer it before you're asked "how would you test this?"

  • Behavioral proof over inspection: "I'd prove the stale-offer gate with a test that seeds an expired offer and asserts it's filtered." Reading the filter function isn't proof.
  • Red before green: for a bug fix, the regression test fails on the old code and passes on the new. If it passes both ways it proves nothing.
  • The testing pyramid (wide cheap base, narrow expensive top):
    • Unit tests on the eligibility predicate and the reducer transitions; cheap, run on every save.
    • A few integration tests on the fetch-render-error path.
    • One or two end-to-end tests on the full apply flow; expensive, so keep them few.
  • New branch, new test. Every new error path, fallback, or condition gets at least one test. No exceptions.

Provenance over resemblance

The sharpest move and the most under-used. Any check that grants permission, hides something, classifies a record, or picks a route must key on a field written on purpose, not on something that merely looks right.

  • Provenance: a value stamped at the point of intent. A server-set placement: 'sponsored' field, a canonical kind, a resolved source.
  • Resemblance (inference): guessing from a shape. "The id starts with sp_," "it has a highlight color," "the array is empty." These break the day something else happens to match.
  • To decide whether an offer is sponsored, key on the stamped field, not the id prefix. To authorize a user, key on the server's session claim, not a client-set flag.
  • If you truly must infer, prove it with a spoof case: a look-alike that matches the heuristic but must not trigger the behavior, and a test that confirms it doesn't.

This is your attribution and identity material given a name: credit and permission decisions ride on provenance, never on what a value happens to resemble.

Know your verification ceiling

Match each claim to whoever actually owns its truth, and don't prove it with the wrong tool. Admitting what your tests can't prove reads as seniority, not weakness.

  • Your unit tests prove your code calls the lender API correctly. They can't prove the lender honors the contract; that needs a contract test against their sandbox or a real integration.
  • A mocked response never proves a third-party contract. A green local test never proves product intent. Jsdom never proves real browser-chrome behavior.
  • When proof can't reach the owner, say so and route around it: drop the claim, test against the real surface, or flag the caveat. Don't paper over it with a local test that proves something adjacent.

Detection needs a recourse

Frontend-native and most candidates miss it. Any state that surfaces a problem to the user needs at least one way out.

  • An error banner needs a retry. An empty state needs a next action. A degraded-mode notice needs an alternative path.
  • "The 'no offers found' state isn't done until it tells the user what to change: adjust income, try a different loan amount." An empty state with no exit is a dead end.
  • Recourse means one of: dismiss, retry, navigate to a fix, or take an alternative path.

Working with AI: adversarial, non-self-certifying

The single most important thing to say about an AI-augmented workflow. In an AI-first interview this sentence is the whole ballgame.

  • "I don't merge what the model wrote because it looks right. I review it adversarially, and I lean on deterministic checks it can't talk its way past: types, tests, a lint gate, CI."
  • The AI accelerates the draft; the verification is yours and it's structural.
  • Independent review beats self-review. A second pass that didn't write the code catches what the author rationalized.

The meta-principle: make the bug unrepresentable

Prefer designs where the wrong thing can't be expressed, over tests that catch it after the fact. This is the thesis behind every move above and a strong closing line.

  • A discriminated union so the UI can't be loading and errored at once.
  • Required props so a card can't render without its eligibility status.
  • Types at the trust boundary so an unvalidated payload can't reach your logic.

"I'd rather make the bug impossible to express than write a test that catches it after the fact."

Jargon caveat: use the moves in plain language. The interviewer won't know internal terms, and dropping them reads as borrowed. Say "prove, don't assert," "provenance over resemblance," "every error needs an exit," not the names of any framework. The discipline transfers; the vocabulary stays in your head.

Multi-Step Application Flow

What it is

A wizard form that collects an application over several steps (income, then employment, then SSN), where the user's answers survive moving between steps, refreshing, or leaving and coming back. It's an online flow: the server validates each step and the SSN goes straight to the server.

  • State persists across steps, so step 3 still knows what step 1 collected.
  • Progress is saved after each step, so a refresh or a dropped connection doesn't wipe the form.
  • Resume is supported: a user who leaves can return and continue from where they stopped.
  • Each field and step validates before advancing: SSN format, currency masking, required fields.
  • Attribution params ride through every step alongside the user's answers.
  • Timeouts are handled: a partner API or session can expire mid-flow, so the UI shows a clear state and lets the user retry.
  • Each step's status is explicit (untouched, valid, submitting, error), so the UI can't show a broken combination.

The safe resume pattern

The client holds a key; the server holds the data.

  • PII fields POST to the server after each step. The server persists them, tokenized, keyed by the session.
  • The client stores only a session id in an httpOnly, Secure, SameSite cookie. JavaScript can't read it, so an XSS bug can't steal it.
  • Non-PII progress (current step, selected loan amount, preferences) can go in localStorage or sessionStorage for a smooth refresh.
  • Resume sends the session id; the server returns the saved state. The SSN never re-enters the browser in plaintext; the user sees a masked field like •••-••-1234.

The security rule that decides placement

localStorage, sessionStorage, and IndexedDB are readable by any JavaScript on your origin. One XSS bug exposes everything in them. That single fact drives the rules:

  • Non-sensitive data can live in those client stores.
  • PII never goes in them in plaintext: it's readable by injected script, plaintext on the device, and has no expiry.
  • httpOnly cookies are invisible to JavaScript, which is why session ids and the durable attribution copy live there.
  • Anything sensitive or authoritative stays on the server; the client holds only a session id that unlocks it.

PII Handling On The Client

GET vs POST is about where the value ends up

Both travel inside TLS, so the wire is equally private. A GET puts values in the URL, and the URL is written to browser history, server access logs, and the Referer sent to the next site. A POST keeps values in the body, which none of those record. So identifiers safe to log (subid, clickid) go in the URL over GET; applicant data (SSN, income) goes in a POST body.

iframe isolation for sensitive forms

A cross-origin iframe runs on its own origin with its own DOM, and the same-origin policy prevents the host page's scripts from reading fields inside it. Pass attribution in through the frame src, keep the SSN inside the frame, and post only non-sensitive events (resize, step-complete) back to the parent via postMessage. A script SDK that renders into the host DOM gives full styling control but lets the host's scripts read what the user types, which suits an offer carousel and rules out SSN capture.

  • On postMessage: set an explicit targetOrigin on send, and validate event.origin on receive before trusting the payload.
  • Harden the frame with CSP frame-ancestors, the iframe sandbox attribute, and a tight referrerpolicy.

Past capture, the value is tokenized server-side and only one service can read it back, so the token flows through the rest of the app instead of the SSN.

Attribution Capture

Capture, persist, re-inject

The source of a lead enters as URL params and must survive every navigation to the outbound lender handoff.

  • Capture at entry: read known params once with URLSearchParams, against a whitelist.
  • Persist first-party: an httpOnly cookie as the durable copy, localStorage as a fallback, stamped with a first-seen time so a later visit keeps first-touch.
  • Re-inject on every hop: decorate internal links and the outbound redirect so a param stripped somewhere still reaches the next page.
  • Skip the referrer: browsers default Referrer-Policy to strict-origin-when-cross-origin, so a cross-site hop drops the path and query, and every hop to a lender is cross-origin.
  • The server mints a lead id and stores the attribution against it, so the URL is a convenience and the server holds the record.
Attribution models: first-touch credits the introducing source; last-touch credits the final click before conversion (common in lead-gen billing); multi-touch splits credit across touches. Stitching an anonymous click to a later logged-in conversion happens server-side via an identity graph; the client just carries both ids.

Event Collection (Right-Sized)

What the client owes for telemetry

For an online application, assume connectivity. Telemetry (clicks, page views) still fires on flaky mobile connections, so it needs modest resilience, not an offline subsystem.

  • Each event carries a client-generated event_id (UUID) so the server can dedupe.
  • Batch events and flush on a size or time threshold to cut request count.
  • Retry a failed send with exponential backoff and jitter.
  • Flush on page unload with navigator.sendBeacon(), which survives the page teardown a normal fetch doesn't.
  • The client stamps occurred_at so an event that arrives late still buckets into the right time on the server.
  • Sample high-volume, low-value signals from the client and record the rate.
Scope note: IndexedDB queues and Service Worker Background Sync are for genuinely offline-first apps (field sales, inspections). A credit card funnel assumes online; the resilience that matters is session and timeout handling, not offline sync.

Rendering The Offer List

What it is

Fetch offers from an API, show them as cards, let the user sort and filter, and handle every state the fetch can be in. This is the most likely shape of the coding round, and it's their core surface.

  • Fetch on mount; model the lifecycle as a discriminated union (idle, loading, success, error) so impossible states can't render.
  • Render all states, including empty: success with zero results is a real state, and it shows "no offers match," not an error.
  • Sort by APR, term, monthly payment, or "recommended." Sorting is a pure function over the array; return a new array with [...offers].sort() so React sees a new reference and re-renders. offers.sort() mutates in place and the change is invisible.
  • Filter by loan amount or credit tier. Debounce the filter input (~300ms) so you refilter after the user pauses, not on every keystroke.
  • Compute the sorted and filtered list during render from raw offers plus the controls. Storing it in separate state synced by an effect is the classic stale-value bug.
  • Use the offer's canonical id as the React key, never the array index.
  • Virtualize (react-window, TanStack Virtual) only if the list runs to hundreds of rows; skip it otherwise.
  • The apply link carries attribution via decorateUrl; applicant data never goes in that URL.
  • Prefer skeleton placeholders over a spinner for perceived speed.

Form Validation And Input Masking

What it is

Check inputs as the user types and before submit, and format fields like SSN and currency as they're entered.

  • Validate per-field on blur or change for fast feedback, and per-step before advancing the wizard.
  • Two layers: client validation for responsiveness, server validation as the real gate. The client's check is a convenience; the server's is the authority.
  • Use a schema validator (zod or yup) to declare the rules once, and react-hook-form to manage field state, errors, and submission with few re-renders.
  • Mask as-you-type: SSN as ###-##-####, currency as $1,234. Keep the raw value separate from the displayed value so you submit clean data.
  • Announce errors accessibly: link the message with aria-describedby, set aria-invalid, and move focus to the first error on submit.
  • react-hook-form uses uncontrolled inputs (refs) for performance; know that tradeoff against fully controlled inputs.
  • Validate an SSN without echoing it into the URL or a log line.

Server-side validation in Node/TS

The client check is UX; the server check is the trust boundary. The pattern that matters more than the library: parse every inbound payload against a declared schema at the server boundary, reject on failure, and derive one schema that both the React form and the API route use.

Libraries: zod is the default now, with valibot (lighter), Yup, Joi, and ajv (raw JSON Schema) as alternatives; NestJS ships class-validator.

// schema.ts — shared by the form (via zodResolver) and the route
export const Application = z.object({
  income: z.number().positive(),
  ssn: z.string().regex(/^\d{3}-\d{2}-\d{4}$/),
})

// route handler — the real gate
const result = Application.safeParse(await req.json())
if (!result.success) return Response.json({ errors: result.error.flatten() }, { status: 400 })
const data = result.data // typed and validated past this line

Parameterized queries stop SQL injection

Validation checks the shape of input; parameterization stops that input from being read as code. They're separate defenses, and you want both. The rule: never concatenate user input into a query string.

// Vulnerable: the input becomes part of the SQL
db.query(`SELECT * FROM users WHERE email = '${email}'`)
// email = "' OR '1'='1" returns every row

// Safe: the driver binds the value as a parameter, never parsed as SQL
db.query('SELECT * FROM users WHERE email = $1', [email])

// An ORM/query builder parameterizes for you
prisma.user.findUnique({ where: { email } })

Handling A Slow Or Failing Partner API

What it is

What the UI does when offers are slow to load or a lender's API is down. This is the online resilience that actually matters for this flow.

  • Time out the request with AbortController plus a timer, so a hung call doesn't spin forever.
  • Show a loading state immediately, with skeletons.
  • On error, show a clear message and a retry button; auto-retry transient failures with backoff.
  • Render partial results: if you query several partners and one fails, show the offers that returned instead of failing the whole page.
  • Wrap subtrees in a React error boundary so a render-time crash shows a fallback, not a blank screen.
  • Distinguish error types: a 4xx is a bad request (don't retry), a 5xx or timeout is transient (retry-able), a network error means offline.
  • Show cached offers while refetching (stale-while-revalidate via React Query or SWR).
  • Cancel the previous request when the query changes (AbortController), so a slow old response can't overwrite newer results.

AbortController vs a generation counter for stale responses

Both guard against an old response overwriting a newer one; they work at different points and complement each other.

  • AbortController cancels the in-flight request when a new one starts. The browser stops the fetch and its promise rejects with an AbortError, so the stale response never arrives and the network connection is freed. This is the primary tool: it prevents the wasted work.
  • Its limit: it only helps when you can cancel in time. If a response already came back and is mid-processing, or the same query fires twice (A→B→A) so you can't tell the two apart by value, abort alone can miss it.
  • A generation counter is a number incremented on every query change. Each request captures the current value; when it resolves, you compare captured against current and discard the result if they differ. It doesn't stop the request, it decides whether to apply the result, which catches any stale write including the identical-query ABA case.
  • Complementary: AbortController cancels the network work, the counter is the correctness backstop that commits only the latest request's result. Belt and suspenders.
  • React Query and SWR do both for you: they track the latest query key, ignore stale responses, and cancel in-flight requests, so you rarely wire this by hand.

Session Management And Timeouts

What it is

How the app knows who the user is across requests, and what happens when that identity expires mid-application.

  • A session is a server record keyed by an id in an httpOnly cookie; the browser sends the cookie automatically on each request.
  • Idle timeout: the session expires after N minutes of inactivity. Financial apps use short windows, around 15 minutes.
  • Absolute timeout: the session expires a fixed time after login regardless of activity.
  • On expiry mid-flow: detect the 401, show a "session expired" state, keep the non-PII progress, prompt re-auth, then resume.
  • Sliding sessions extend on activity; token-based auth uses a short-lived access token plus a refresh token.
  • Warn before logout: a "you'll be signed out in 2 minutes" modal with a keep-alive button, common in banking.
  • Server session (opaque id, easy to revoke) vs JWT (self-contained claims, hard to revoke, so it needs short expiry and refresh).

Cookie Flags

The settings that control who reads a cookie and when it's sent

  • httpOnly: JavaScript can't read it via document.cookie. Blocks XSS from stealing it. Use for session ids.
  • Secure: sent only over HTTPS.
  • SameSite: controls cross-site sending. Strict never sends cross-site; Lax sends on top-level navigations only; None always sends and requires Secure. Lax and Strict mitigate CSRF.
  • Domain / Path: scope which URLs receive the cookie.
  • Expires / Max-Age: lifetime. A session cookie with no expiry dies when the browser closes.
  • Size: ~4KB, sent on every matching request, so store an id, not data.
Why Lax is the sensible default: Strict withholds the cookie when a user arrives from any other site, including their own email or a partner link, so they land logged out on the first navigation. In a marketplace where users arrive from publisher links, that breaks entry. Lax sends the cookie when following a link but not on cross-site subrequests, which stops CSRF while keeping arrivals working. Modern browsers default to Lax when the attribute is omitted.

How an httpOnly cookie is managed without JavaScript

An httpOnly cookie lives in the HTTP layer. The browser stores and transports it; JavaScript is bypassed, but the cookie stays fully active.

  • Created: the server sends a Set-Cookie response header; the browser stores it in a jar JavaScript can't reach.
  • Sent: on every matching request, the browser auto-attaches it as a Cookie request header, and the server reads it there. This happens on navigations, image loads, and fetch/XHR, with no script involved.
  • Updated / deleted: the server sends another Set-Cookie; same name replaces the value, Max-Age=0 deletes it.
  • Cross-origin fetch: cookies ride along only with credentials: 'include' plus the server's Access-Control-Allow-Credentials. Your code still never touches the value.

httpOnly makes the cookie server-only, not inert: the browser is the storage and courier, headers are the interface, and script can't read or steal the id.

Signed cookies

A signed cookie carries a tamper-proof stamp so the server can tell if the value was edited. The server computes an HMAC over the value with a secret key only it holds, and sends value plus signature. When the cookie returns, the server recomputes the HMAC and compares; a mismatch means the value was changed, so it's rejected.

  • Protects integrity, not confidentiality: the value stays readable (base64 encodes, it doesn't encrypt), but it can't be altered undetected.
  • Example: a cookie holding user_id=42. Signing stops a user from editing it to 43 and being accepted.
  • Different job from httpOnly: signing stops tampering, httpOnly stops JS from reading it. Often used together.
  • Signing vs encryption: sign when the client may read but not change the value; encrypt when the client must not read it either.
  • For an opaque random session id pointing to server-side data, signing adds little, since the id is already unguessable and the real data lives on the server. Signing earns its keep when the cookie itself carries meaningful data.
  • Built in: Express cookie-parser signed cookies, Rails signed cookies, Python itsdangerous. A JWT is the same idea in a standard signed-token format.

XSS And CSRF For A PII Form

XSS: an attacker runs their script in your page

Injected script runs with your origin's privileges: it can read localStorage, non-httpOnly cookies, and keystrokes. On a PII form that's a direct SSN leak.

  • Escape output. React escapes by default; avoid dangerouslySetInnerHTML, and sanitize with DOMPurify if you must render HTML.
  • Set a Content Security Policy to restrict which script sources can run.
  • Keep session ids in httpOnly cookies so injected script can't read them.

A typical CSP

The header restricts where scripts, styles, images, and connections can come from, so an injected resource has no allowed source and the browser refuses it.

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-r4nd0m';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self' https://api.example.com;
  font-src 'self';
  frame-ancestors 'none';
  form-action 'self';
  base-uri 'self';
  object-src 'none';
  upgrade-insecure-requests;
  • script-src 'self' 'nonce-...' is the core XSS control: only your own scripts and inline scripts carrying the server-generated nonce run, so injected <script> with no nonce is refused. Next.js sets the nonce via middleware.
  • default-src 'self' is the fallback for any directive you didn't name: same-origin only.
  • frame-ancestors 'none' blocks clickjacking, replacing X-Frame-Options.
  • connect-src whitelists where fetch/XHR/WebSocket can talk, so exfiltration to an attacker's domain fails.
  • object-src 'none' and base-uri 'self' close two classic bypass routes (plugins, <base> hijacking).

Watch the weak spot: 'unsafe-inline' on script-src gives back most of the protection, so keep it off scripts. It's a tolerable compromise on style-src, which is the one shown here.

CSRF: an attacker makes the user's browser send an unintended request

Because the browser auto-sends cookies, a malicious page can trigger an authenticated request to your server on the user's behalf.

  • Set SameSite=Lax or Strict so the cookie isn't sent on cross-site requests.
  • Use a CSRF token: a per-session secret the form submits and the server verifies.
  • Check the Origin or Referer header on state-changing requests.
How the synchronizer token and Origin check work

Synchronizer token (the classic CSRF token). The server generates a random secret tied to the session, embeds it in the page (a hidden form field or a <meta> tag the client reads into a request header), and requires it back on every state-changing request. The server compares the submitted token to the one stored for the session and rejects a missing or mismatched value. An attacker's cross-site page can't read your page's DOM, blocked by the same-origin policy, so it can't obtain the token to forge the request.

Double-submit variant (stateless). The server puts the token in a cookie and the client echoes the same value in a header; the server checks the two match. No server-side token storage, which is why SPAs and stateless APIs favor it.

Origin / Referer check. On any POST, PUT, or DELETE, read the Origin header (fall back to Referer) and compare it to your own origin, rejecting a mismatch. It's cheap and needs no per-request secret, so it's a solid second layer behind SameSite and a token. In practice: SameSite as the baseline, a token for sensitive actions, an Origin check behind both.

The storage rules and cookie flags already chosen (PII on the server, session id in an httpOnly, SameSite cookie) are the concrete defenses here.

Accessibility For Financial Forms

What it is

The form works for keyboard and screen-reader users, which is also a legal requirement under ADA and WCAG for a consumer financial product.

  • Every input has a real <label> tied by htmlFor/id.
  • Announce errors: aria-describedby links the message, aria-invalid marks the field, and role="alert" or an aria-live region speaks dynamic errors.
  • The whole flow is keyboard-operable with a visible focus ring and a logical tab order.
  • Masked inputs read sensibly to a screen reader; provide a clear format hint rather than raw punctuation.
  • Never signal an error by color alone; add text or an icon.
  • WCAG 2.1 AA is the common bar. Test keyboard-only, with a screen reader (NVDA or VoiceOver), and with axe DevTools.

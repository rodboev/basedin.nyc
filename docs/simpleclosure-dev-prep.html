Why the work is split into isolated PRs

The submission has six PRs, each merged independently: scaffold, data layer, grid and cards, filter and sort controls, polish, and genre slugs. The reason is testability.

Coupled code can only be verified as a unit. When the data layer, the grid, and the sort logic all live in the same commit, a sorting bug requires reading the fetch code to rule out a data problem, then the grid code to rule out a rendering problem, before you can isolate the comparator. When they're in separate PRs with separate tests, the sort tests run against hand-built fixtures that never touch the network, and a failure in sort.test.ts points at sort.ts and nothing else.

The same principle applies to review. A reviewer looking at the grid PR doesn't need to hold the data layer in their head. A reviewer looking at the data layer doesn't need to understand Tailwind. Each PR has one concern and its own rationale in the commit messages, so the review surface matches the cognitive surface.

The same principle drives separation of concerns in component architecture. Coupled things can only fail together, and diagnosing a failure in a coupled system means eliminating every other piece before you find the one that broke.

The TMDB boundary

Everything TMDB-specific lives in src/lib/tmdb.ts: request construction, response types, image URL assembly, field normalization. Components consume Movie and Genre, normalized types with no TMDB vocabulary. If TMDB renames poster_path to poster or wraps responses in a new envelope, one file changes. The rest of the app keeps working.

The boundary is greppable

Searching src for image.tmdb.org or any raw TMDB field name (poster_path, vote_average, release_date) matches only the data layer and its test fixtures. A grep you can run at any time to verify the boundary holds. The README records this as a verification method.

server-only as a structural constraint

The data layer imports server-only. If a client component tries to import tmdb.ts, the build fails. The constraint is enforced by the compiler: it survives refactors, team turnover, and late-night commits. A code review comment saying "keep this server-side" depends on attention. A build error depends on the compiler. Same principle as making illegal states unrepresentable in a type system.

Normalization: converting raw TMDB fields into your own types

TMDB's API returns movies with null posters, empty release dates, zero vote counts, and absent overviews. These show up on the first page of a low-popularity genre. The mapper defaults every field: absent titles become "Untitled," absent ratings become 0, empty strings and nulls are distinguished. The tests exercise this against a fixture captured from a real sparse TMDB response, so the test data matches what the API actually sends.

// Defaults absent fields instead of passing undefined through
function mapMovie(raw: RawMovie): Movie {
  return {
    id: raw.id,
    title: raw.title ?? "Untitled",
    posterUrl: posterUrl(raw.poster_path),
    rating: raw.vote_average ?? 0,
    voteCount: raw.vote_count ?? 0,
    releaseDate: raw.release_date || null,
    overview: raw.overview ?? "",
  };
}

Why client-side sort over API-side sort_by

TMDB's sort_by=vote_average.desc sorts across the entire catalog with no minimum vote threshold. The first result is a movie with 3 votes and a perfect 10.0. TMDB's own charts apply a vote-count floor to avoid this; the raw API doesn't. An unfloored sort surfaces titles nobody has heard of above movies with thousands of reviews.

The brief says "first page is sufficient." API-side sort changes which 20 movies you get. Client-side sort reorders the 20 you already have. Those are different operations. The API's popularity ordering already does the hard work of surfacing movies people have actually watched. Sorting that page by rating gives you recognizable movies in rating order, and the interaction is instant because there's no round-trip.

The flaw is invisible unless you check the data. An API-side sort returns 20 movies with high ratings. It looks correct. You only discover the problem by inspecting vote counts and recognizing that 10.0 on 3 votes is noise.

The comparator (the arrow function inside .sort()) handles three edge cases

export function sortMovies(movies: Movie[], key: SortKey, dir: SortDir): Movie[] {
  const flip = dir === "desc" ? -1 : 1;
  return [...movies].sort((a, b) => { ... });
}
  • Ties break by vote count: two movies rated 6.4 are ordered by confidence, not left in arbitrary order. The movie with 4,000 votes ranks above the one with 900.
  • Unknown release dates sink to the bottom: a null release date goes last regardless of sort direction. Date ascending should show the oldest movie first, and "unknown" means "no date," which belongs at the end.
  • It copies before sorting: [...movies].sort() instead of movies.sort(). In-place Array.sort mutates the array. React compares references to detect state changes. Mutating the same array and calling the setter with the original reference means React sees no change and skips the re-render. The sort silently does nothing. Easy to write, hard to spot.

States and edge cases

Filter goes to the API; sort stays on the client

Genre changes the result set, so it travels to TMDB as with_genres and lives in the URL via searchParams. Every filtered view is shareable and bookmarkable. Sort only reorders the 20 movies already fetched, so it stays in plain client state: useState for the key and direction. Syncing sort to the URL would add router machinery whose only benefit is a shareable sort order over 20 items.

This asymmetry is the interesting part. Filter and sort both appear as dropdowns in the UI, but they have different data-flow semantics. One changes the dataset, the other rearranges it. Routing the filter through the URL and keeping the sort in state encodes that distinction structurally.

Refetch feedback during genre changes

Next's App Router keeps the current page visible during same-route searchParams navigation. The loading.tsx skeleton shows exactly once, on the initial cold load. After that, switching genres shows nothing: the old grid stays on screen while the server fetches the new results, and then the new grid replaces it with no visual feedback that anything happened.

The fix is a useTransition wrapper around the router push. The genre change runs inside startTransition, which sets isPending to true while the navigation resolves. The grid container gets aria-busy and dims to half opacity. The old results stay visible (better than a flash to skeleton), and the dim makes the wait legible on slow connections.

const [isPending, startTransition] = useTransition();
// ...
startTransition(() => {
  router.push(value === "all" ? "/?genre=all" : `/?genre=${value}`);
});
// ...
<div
  aria-busy={isPending}
  className={`motion-safe:transition-opacity ${isPending ? "opacity-50" : "opacity-100"}`}
>

Empty state

If a genre filter returns no movies, the grid renders "No movies matched this filter. Try another genre." With genre-only filtering against TMDB's catalog this is near-unreachable (every genre has results), so it gets one conditional and one test. The point: a blank grid reads as a bug. A sentence reads as an answer. The cost is one if statement.

Null posters are real

TMDB returns null posters on live pages. A sparse-page fixture captured from the API has 3 of 20 movies with no poster. Those cards render a styled placeholder showing the title in the poster slot, with role="img" and an aria-label for screen readers. The test uses that real sparse fixture, so the coverage comes from actual API data.

Zero-vote titles hide the badge

Unreleased movies arrive with a vote average of 0.0 over 0 votes. A red "0.0" badge would misread as a real rating rather than an absence of one. Movies with voteCount === 0 render no badge. The distinction is between "this movie was rated 0" and "nobody has rated this movie."

Genre slugs and URL canonicalization

?genre=science-fiction is an address. ?genre=878 is a lookup key. The URL uses slugs derived from the fetched genre names, so the address is human-readable and stable across API changes. Any non-canonical path (bare /, numeric ids, case variants, repeated params) redirects to its canonical slug URL with a history replacement, so the address bar always settles on a complete, shareable URL and Back returns to the previous page instead of looping through redirect intermediates.

The slug generator handles collisions: if two genre names slugify to the same string (e.g., "A&B" and "A B" both become "a-b"), the second gets an id suffix. If a name has no alphanumeric characters at all, the slug falls back to the genre id. The test covers both cases against hand-built collision fixtures.

What the tests prove

Four test files in Vitest: tmdb.test.ts, sort.test.ts, MovieCard.test.tsx, DiscoverView.test.tsx. Each file covers one layer and stays within it. The tests collectively close a requirements trace: one row per requirement, each mapping to the file that fulfills it and the test or observation that proves it.

Fixtures

A fixture is a captured real API response saved as a JSON file. Three live in src/test/fixtures/: discover.json (a full 20-movie page), discover-sparse.json (a page with null posters and empty dates), and genres.json (the genre list). Tests stub fetch and return these fixtures instead of hitting the network.

The alternative is hand-building test objects: { id: 1, title: "Test Movie", rating: 7.5 }. That approach tests against what you imagine the API sends. Fixtures test against what the API actually sends. If TMDB nests ratings inside a new scores object tomorrow, hand-built tests still pass because they never had the old shape; fixture-based tests break, which is correct, because the mapper hasn't been updated for the new shape.

Sort tests are the exception: they use four hand-built movies with deliberate ratings and dates, because the sort comparator's job is ordering logic, not data fidelity. Fixtures for sort would couple the test to TMDB's response when the comparator has nothing to do with TMDB.

Data layer tests (tmdb.test.ts)

Two concerns: request construction and response mapping.

Request tests verify the URL, params, and error handling. They check that with_genres appears when a genre is selected and is absent when it isn't. They check that a missing API key throws before making a network call, and that a non-OK response throws instead of silently returning malformed data.

Mapping tests run against the captured fixtures. The first movie in the discover fixture is checked field by field. The sparse fixture exercises null posters, empty release dates, and absent overviews. A minimal fixture ({ id: 42 } with everything else absent) verifies that every default fires. The tests pin to the contract TMDB actually serves.

Sort tests (sort.test.ts)

Seven tests against four hand-built movies with deliberately chosen ratings, vote counts, and release dates. The fixtures are designed to exercise tie-breaking (two movies with rating 6.4 and different vote counts), null handling (one movie with no release date), and immutability (the input array is unchanged after sorting). Each test asserts the full ordering, not just the first element.

Component tests (MovieCard.test.tsx)

Cards render from the real mapping layer's output. The test for null posters finds a posterless movie in the sparse fixture and renders it. Badge color thresholds are parametrized: [7.0, "high"], [6.9, "mid"], [5.0, "mid"], [4.9, "low"] cover the exact boundary values.

One test pins the overlay's CSS utility classes directly. It exists because the Tailwind v3-to-v4 migration broke the gradient: bg-gradient-to-t compiles to nothing in v4 (the correct class is bg-linear-to-t). The overlay shipped with no background at all; overview text was invisible against light posters. The test is ugly, but jsdom doesn't compute CSS, so asserting the class name is the only way to catch this regression.

View tests (DiscoverView.test.tsx)

The view tests mock next/navigation and verify three things: genre changes navigate via URL (calling router.push), sort reorders the existing cards with zero network traffic (a fetch spy asserts zero calls), and switching the sort property resets direction to descending.

The zero-traffic assertion is the one that matters most. It encodes the filter/sort asymmetry as a testable invariant. If someone refactors the sort to re-fetch from the API, this test breaks.

How AI tooling was used

The submission was built with AI assistance. Nimrod said the exercise "may be beneath your level," and the evaluators will assume AI use. What matters is how the output was verified.

Verification through the Tailwind migration bug

The overlay originally used bg-gradient-to-t, a Tailwind v3 class that compiles to nothing in v4. The overlay rendered with no background. Overview text was invisible against light posters. The happy path looked fine because most posters are dark. A test that pins the actual class names in the DOM caught it. The fix was one line: rename to bg-linear-to-t.

The cycle: generation produced code, a test caught the error, the fix was mechanical. Generation is fast. Verification is where quality comes from.

Verification through the sort decision

The default AI-generated approach would use sort_by=vote_average.desc because it's the obvious API parameter. Inspecting the actual response revealed the junk-rating problem: 10.0 on 3 votes at the top. The decision to sort client-side came from looking at real data.

Structural constraints

Compiler-enforced and test-enforced constraints survive regardless of who writes the next change. The Tailwind class test catches gradient regressions on any future migration. The copy-before-sort test (expect(sorted).not.toBe(input)) catches the in-place mutation bug even if the developer has never encountered it. The server-only import makes an accidental client-side data layer import a build error.

SimpleClosure's JD says "trusts but verifies." Concretely, that means tests that catch failure modes you weren't specifically looking for.

The Business You're Interviewing For

What Engine actually is

Engine by MoneyLion is the former Even Financial: an embedded-finance marketplace. A publisher or landing page sends a consumer into a funnel, Engine matches that consumer to lenders, card issuers, and insurers across 60-plus product types, and the financial institution pays per qualified lead. Because the payout attaches to a specific publisher and a specific click, attribution is the product itself. Their integration docs thread client tags such as subID, clickID, and traffic source through every hop and settle payouts per lead against them.

The two rules that unify every question he asked

Provenance is revenue. The source of a lead travels as explicit, persisted data that any downstream service can read on demand.

PII is liability. A Social Security number stays out of anything that can leak: URLs, Referer headers, server logs, browser history, and analytics beacons. Attribution identifiers belong in the URL; applicant data never does.

His GET-versus-POST question, his referrer-architecture frustration, and his interest in observability all resolve to these two rules. Say them out loud and you're on his frequency.

Attribution: Where Provenance Lives

Why the Referer header can't carry it

The Referer header and document.referrer report where a request came from, and both decay the moment traffic crosses origins. Modern browsers default Referrer-Policy to strict-origin-when-cross-origin, so a cross-site navigation sends only the origin, drops the path and query, and sends nothing at all on an HTTPS-to-HTTP hop. rel="noreferrer", privacy extensions, and corporate proxies strip more. Every redirect from the marketplace to a lender is cross-origin, so a design that recovers the source by reading the referrer starts broken and degrades further in the browsers privacy-conscious users run. This is almost certainly the bug the hiring manager was reworking.

The browser change behind his HTTP/2 comment

His memory garbled two separate things, and the correct version is worth carrying in. HTTP/2 still sends the query string (see the transport section). What genuinely changed recently is that browsers now strip tracking parameters from URLs. Since Firefox 102, Firefox removes known tracking params such as fbclid and mkt_tok from URLs under strict tracking protection and private browsing, and it strips them on redirects too. Brave and Safari trim comparable params.

The strip-lists target known third-party trackers, so a first-party subID usually survives. Leaning on utm_* or on the referrer to reconstruct a lead's source will still lose data in those browsers. The durable answer keeps attribution first-party and server-owned, so a stripped or absent URL param costs nothing.

The pattern that survives the whole funnel

Capture, persist, re-inject. Three moves carry the source from entry to the lender handoff.

Capture at entry. Read the params once with URLSearchParams against a whitelist of your keys.

const KEYS = ['subid', 'clickid', 'utm_source', 'utm_campaign', 'partner']
const incoming = new URLSearchParams(location.search)
const attribution = {}
for (const k of KEYS) {
  const v = incoming.get(k)
  if (v) attribution[k] = v
}

Persist first-party. Store the values where a later page reads them: a server-set httpOnly cookie for the durable copy, localStorage as a client fallback, stamped with a first-seen time so you hold first-touch.

Re-inject on every hop. Decorate internal links and the outbound redirect so the source rides along.

function decorateUrl(href, attribution) {
  const url = new URL(href, location.origin)
  for (const [k, v] of Object.entries(attribution)) {
    if (!url.searchParams.has(k)) url.searchParams.set(k, v)
  }
  return url.toString()
}

Own it server-side. Mint a lead id at entry and store the attribution against it, so the URL becomes a convenience and the server record is the source of truth. Source captured once, owned server-side, readable by every downstream consumer: that's the architecture he described rebuilding.

GET, POST, and What Rides the Wire

The real difference, which is observability

GET and POST both travel inside TLS, so wire secrecy is a wash. The difference is where the URL goes afterward. A GET puts parameters in the URL, and the URL lands in browser history, server access logs, proxy logs, and the Referer sent to the next origin. A POST keeps them in the request body, which none of those record by default. Write an SSN into a query string and you've copied it into logs you don't control and handed it to whatever site the user visits next. That's the practical answer he liked, and it's why POST carries applicant data while GET carries only identifiers that are safe to log.

What HTTP/2 changed, precisely

HTTP/2 still delivers the query string. It moves inside the :path pseudo-header, compressed with HPACK and wrapped in TLS; HTTP/3 does the same with QPACK. The server decodes it, access logs record it, and a third party can still receive it through the Referer. HTTP/2 changed the framing and header compression on the wire, and left untouched whether the query reaches the far end. If he raises "HTTP/2 stopped sending params," the graceful correction is that HTTP/2 compresses the path into a header stream, and the param still arrives and still logs; the leak he cares about is a browser and logging concern, not a protocol one.

Signed Cookies, Tokens, and Storing PII

Signed cookies, explained simply

A signed cookie is a value plus a fingerprint only your server can produce. The server computes an HMAC of the value with a secret key and sends value plus signature. When the cookie comes back, the server recomputes the HMAC and compares. Edit the value in devtools and the two signatures diverge, so the server rejects it. Signing proves integrity. It hides nothing, because the value still travels readable (base64 encodes, it doesn't encrypt).

  • It's an HMAC over the value with a server-only secret: tamper-evident, still readable.
  • Keep the secret on the server, rotate it, and accept several keys during rotation.
  • Pair it with httpOnly, Secure, and SameSite so script can't read it, it's TLS-only, and cross-site sends are constrained.
  • Batteries exist: Express cookie-parser signed cookies, Python itsdangerous, Rails signed cookies.

Signed versus encrypted versus JWT

Signing and encryption answer different questions. Sign when the client may read the value but must not change it, such as a user id or a cart id. Encrypt when the client must not read it either; Rails encrypted cookies and encrypt-then-MAC schemes cover that case. A JWT is a signed token in a standard envelope, handy in a cookie or an Authorization header, and it exposes its claims to anyone who holds it unless you also encrypt it. For anything genuinely secret, the strongest option keeps the data server-side and puts only an opaque session id in the cookie.

Tokenization: where PII lives when it isn't in a cookie

Storing sensitive data well starts with keeping it out of the browser. The client holds a reference; the value lives server-side. Three homes for the value:

  • A server-side session store (Redis, Postgres) keyed by a session id in an httpOnly cookie. The browser holds the key, the server holds the data.
  • A signed or encrypted token that carries only non-sensitive claims, so nothing private rides along with it.
  • A PII vault that swaps the SSN for a token and stores the real value encrypted under tight access control. Vendors like Skyflow and Basis Theory sell this, and PCI DSS formalizes the approach for card data.

For an SSN in a prequalification flow: capture it over POST and TLS, tokenize it immediately, pass the token through the funnel, and decrypt only inside the one service that submits to the lender. The blast radius shrinks to a single service instead of your whole frontend.

Embedding on Third-Party Sites

postMessage and CORS don't gate each other

postMessage and CORS sit on different layers. CORS controls cross-origin HTTP requests made by script with fetch or XHR, and the server grants access with Access-Control-Allow-Origin. postMessage moves messages between browsing contexts, a page and its iframe or a popup, across origins, and the server plays no part. A cross-origin iframe can't touch the parent DOM under the same-origin policy and can't call the parent's API without CORS, yet it can postMessage to coordinate. So an embedded offer widget posts events outward (resize, step-complete) and fetches its own data from its own origin, where CORS never enters the picture.

Two habits keep it safe: set an explicit targetOrigin on send and never '*' for anything sensitive; validate event.origin on receive and treat the payload as untrusted input.

iframe versus SDK decides who can read the SSN

The embedding choice is a security boundary. An iframe runs on its own origin with its own DOM, so the host page can't read fields inside it. That isolation is the reason PII forms belong in an iframe: pass attribution in through the frame src, keep the SSN inside, post only non-sensitive events back.

A script SDK renders into the host's DOM for full styling control, which also lets the host's scripts read whatever the user types. That suits an offer carousel and disqualifies SSN capture. Harden the frame with CSP frame-ancestors, the iframe sandbox attribute, and a tight referrerpolicy.

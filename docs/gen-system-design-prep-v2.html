System Design: Frontend Focus (v2)

Technical reference for the client, the client-to-server contract, and the production frontend of a telemetry/metrics system. Definitions, APIs, and code you can study. The v1 doc holds the backend detail if you want it.

Sections

The Event Contract

The envelope the client emits

Agree on one shape for every event so the backend never special-cases a producer. A workable envelope:

{
  "event_id":   "6f9c...e2",   // UUID the client generates; used to de-duplicate
  "event_type": "offer_click",
  "occurred_at":"2026-07-14T15:04:03.221Z", // when it happened, stamped on the client
  "anonymous_id":"a1b2...",    // device/cookie id, present before login
  "user_id":     null,         // stable id, present after login
  "context": { "page_url": "…", "subid": "partnerX", "clickid": "…" },
  "properties": { "offer_id": "loan_4417", "apr": 12.9, "position": 3 }
}
The client stamps occurred_at. A device can be offline when the action happens, so the event's real time is set on the client, not when the server receives it. This is called event time (as opposed to processing time, when the server sees it). Aggregates that bucket by minute or hour must use event time or offline events land in the wrong bucket.
The client generates event_id as a UUID. Browsers use crypto.randomUUID(). It exists so the backend can discard duplicates, which matters because reliable sending from a browser means "retry until acknowledged," and a retry after a lost acknowledgment sends the same event twice. A stable id makes the duplicate a no-op instead of a double count.

Type the envelope as a discriminated union

Key the union on event_type so each event's properties are typed to that specific type, and the compiler rejects a payload that doesn't match:

type Event =
  | { type: 'offer_click';  props: { offerId: string; position: number } }
  | { type: 'page_view';    props: { path: string } }
  | { type: 'app_submit';   props: { leadId: string; stepCount: number } }

function track(e: Event) { /* narrowing on e.type gives you e.props typed */ }

A plain Record<string, unknown> for props would let a wrong field through to production. The union moves that error to compile time. This is the same immutability-and-exhaustiveness discipline that shows up again in the UI state machine below.

Client-Side Collection

The four jobs of a browser analytics SDK

Batch and flush. Buffer events in memory; send them as a group on a size threshold (e.g. 20 events) or a time threshold (e.g. 5s), whichever hits first. One request per click floods the network and the endpoint; batching cuts request count by one to two orders of magnitude.
Send unload events with navigator.sendBeacon(). An event that fires as the user navigates away is lost with a normal fetch, because the browser cancels in-flight requests when the document unloads. sendBeacon queues the request with the browser to send in the background, and it survives the teardown. Use it in a visibilitychange/pagehide handler to flush the buffer on exit. It is limited to POST and can't read the response, which is fine for fire-and-forget telemetry.
Buffer offline. Persist the unsent queue to localStorage (simple, ~5MB, synchronous) or IndexedDB (larger, async) so a crash or dead connection doesn't drop it. Drain the persisted queue on next load before enqueuing new events.
Retry with exponential backoff and jitter. On a failed send, retry after 1s, 2s, 4s, 8s, each with a random jitter added, so a server coming back up doesn't get every client retrying in lockstep (a thundering herd). Cap the delay and the queue length so a permanently offline client stays bounded.

Sampling

For high-volume, low-value signals (scroll depth, mouse movement, hover), send a random fraction from the client, say 1–10%, and include the sample rate in the payload so the backend multiplies back up to an estimate. Sampling is a client decision because it's the only place you can cut the volume before it costs anything to transmit or store. Never sample events tied to money or conversions; those need every instance.

Attribution Capture

Capture, persist, re-inject

Source params enter as URL query string and must survive every navigation to the outbound lender handoff.

Capture at entry, against a whitelist so you don't store junk:

const KEYS = ['subid', 'clickid', 'utm_source', 'utm_campaign', 'partner']
const incoming = new URLSearchParams(location.search)
const attribution = {}
for (const k of KEYS) {
  const v = incoming.get(k)
  if (v) attribution[k] = v
}

Persist first-party: a server-set httpOnly cookie as the durable copy, localStorage as a client fallback, stamped with a first-seen timestamp so a later visit doesn't overwrite first-touch.

Re-inject on every hop so a param stripped somewhere still reaches the next page:

function decorateUrl(href, attribution) {
  const url = new URL(href, location.origin)
  for (const [k, v] of Object.entries(attribution)) {
    if (!url.searchParams.has(k)) url.searchParams.set(k, v)
  }
  return url.toString()
}

Why the referrer can't carry attribution

The Referer header and document.referrer report where a request came from, and both decay across origins. Browsers default Referrer-Policy to strict-origin-when-cross-origin: a cross-site navigation sends only the origin, dropping the path and query, and an HTTPS→HTTP hop sends nothing. Every hop from the marketplace to a lender is cross-origin, so a design that recovers the source from the referrer starts broken. Some browsers now also strip known tracking params from URLs (Firefox since 102 removes fbclid, mkt_tok and similar under strict protection), which is why a first-party, server-owned copy is the durable source and the URL param is a convenience.

Attribution models

First-touch: full credit to the source that first introduced the user.
Last-touch: full credit to the final click before conversion. Most common in lead-gen billing because it maps to the click that immediately preceded the lead.
Multi-touch: credit split across touchpoints (linear, time-decay, or position-based weighting).

Stitching an anonymous click to a later logged-in conversion is done server-side with an identity graph mapping each anonymous_id to a user_id. The client's job is only to carry both ids on the events so the join is possible.

PII Handling

GET vs POST is about where the data ends up, not secrecy

Both travel inside TLS, so the wire is equally private. The difference is what records the URL afterward. A GET puts values in the URL, and the URL is written to browser history, server access logs, proxy logs, and the Referer sent to the next origin. A POST keeps values in the request body, which none of those record by default. So identifiers that are safe to log (subid, clickid) travel in the URL over GET; applicant data (SSN, income) travels in a POST body. Writing an SSN into a query string copies it into logs you don't control and hands it to whatever site the user visits next.

iframe isolation for PII forms

A cross-origin iframe runs on its own origin with its own DOM, and the same-origin policy prevents the host page's scripts from reading fields inside it. That isolation is why sensitive forms belong in an iframe: pass attribution in through the frame src, keep the SSN inside the frame, and post only non-sensitive events (resize, step-complete) back to the parent via postMessage. A script SDK that renders into the host DOM gives the host full styling control but also lets the host's scripts read anything the user types, which suits an offer carousel and disqualifies SSN capture.

postMessage safety: set an explicit targetOrigin on send (never '*' for anything sensitive), and validate event.origin on receive before trusting the payload.
Harden the frame: CSP frame-ancestors to control who can embed you, the iframe sandbox attribute, and a tight referrerpolicy.

Past capture, the value is tokenized server-side (swapped for an opaque reference, the real value encrypted in a vault, one service able to read it back). That part isn't a frontend concern beyond knowing the token, not the SSN, is what flows through the rest of the app.

Rendering And Data Freshness

Model async UI as a state machine

Represent the fetch lifecycle as a discriminated union, not separate boolean flags that can contradict each other:

type State<T> =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error'; error: Error }

Separate isLoading and isError booleans allow "loading and error at once," an impossible state that becomes a bug. The union makes that unrepresentable and forces every case to be handled at the render site. Render all of: idle, loading, success, empty (success with zero results, which is not an error and shouldn't show an error UI), and error-with-retry.

Data freshness decides the client pattern

Latency the user feels is mostly set server-side by where the number was computed: precomputed at write time is instant to read, computed on demand answers any query but slower, batch is cheapest but stale. You consume whichever the API offers and pick the matching client pattern:

FreshnessExampleClient pattern
Live (sub-second)A counter or ops tile ticking in near-real-timeServer-Sent Events (one-way server push over a single HTTP connection) or a WebSocket (bidirectional); fall back to interval polling if the API is request/response only
Fresh (seconds)A dashboard the user expects current-ishFetch on load and on demand, cache and revalidate with React Query or SWR, show a "last updated" time so staleness is explicit
Batch (hours/daily)A report reflecting yesterdayPlain fetch of a precomputed summary; surface the as-of date so nobody reads it as live
SSE vs WebSocket: SSE is simpler, auto-reconnects, and runs over plain HTTP, right for server→client streams like a live counter. WebSocket is bidirectional and needed only when the client also pushes frequently (chat, collaborative editing). For dashboards, SSE is usually enough.
Next.js rendering: personalized per-user offers are server-rendered per request (an uncached fetch in the App Router, or getServerSideProps in Pages), not statically generated, because every user sees different data. Static generation only fits content identical for everyone.

The Backend, Briefly

Enough to consume the contract and collaborate

The shape. The client posts events to a collector endpoint; the collector drops them onto a durable log (Kafka or similar) so a traffic spike can't overwhelm the database; a processing job aggregates events and writes to an analytics store the dashboards read.
Delivery guarantees, three levels. At-most-once may drop, never duplicates (cheap, fine for sampled telemetry). At-least-once never drops but may duplicate (the default; duplicates removed downstream via event_id). Exactly-once neither drops nor duplicates (expensive; reserved for money). The browser side of at-least-once is the retry loop plus the idempotency key; the rest is the backend's problem.
Not every event needs the same guarantee. A page view can be lost or double-counted with no harm, so it should be cheap. A payout event is billing, so it needs exactly-once and an audit trail. Splitting the pipeline by event criticality is the one backend tradeoff worth understanding from the frontend seat.

Frontend Production Health

How a frontend engineer measures a healthy production app

Core Web Vitals via Real User Monitoring. Measure real users, not a lab run. LCP (Largest Contentful Paint): time until the main content renders; good is <2.5s. INP (Interaction to Next Paint): responsiveness to user input, which replaced FID in March 2024; good is <200ms. CLS (Cumulative Layout Shift): how much the page visually jumps; good is <0.1. The web-vitals library reports all three from the browser; Vercel Analytics, Datadog RUM, and Sentry ingest them.
Error and session tracking. Sentry captures frontend exceptions with stack traces and tags them by release, so a spike lines up with a deploy. Session replay reconstructs the exact user path into a bug, which finds breaks no server metric shows because they happened in the browser.
Feature flags and gradual rollout. LaunchDarkly or Statsig gate a change behind a flag. Ship it off, enable for a small percentage of traffic (a canary), watch error rate and Web Vitals, then ramp up or flip off without a redeploy. This is how a frontend change is validated in production safely.
Funnel and conversion analytics. Drop-off between application steps, joined back to attribution, is the metric connecting frontend work to revenue. A step where users abandon is a UX or performance problem you can act on.
Performance budgets in CI. Lighthouse CI fails the build on a bundle-size or Web Vitals regression, making performance a gate rather than something noticed after it ships.
